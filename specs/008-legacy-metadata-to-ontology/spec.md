# Feature Specification: 레거시 메타데이터에서 온톨로지까지 — 난독화 예제 시나리오

**Feature Branch**: `008-legacy-metadata-to-ontology`

**Created**: 2026-08-05

**Status**: Draft — **결정 완료 (2026-08-05)**. 두 갈림길이 정해졌다(§결정 기록):
객체화는 **domain-layer 를 번들에 편입**해서 하고, 예제는 **난독화본을 기본**으로 두되 깨끗한
예제를 선택 가능하게 유지한다. 전자는 **헌법 개정을 수반한다** — 온톨로지 쓰기 주체가 둘이 된다.

**Input**: 사용자 지시 — *"예제 업무에 대한 메타데이터 증강, Text2SQL 을 기반으로 온톨로지 객체를
선언 … 지금 예제를 기본 DDL 이 메타데이터가 엉망이어야 함: 릴레이션 정보가 없고, 테이블 및 필드명이
코드로 되어있어 의미를 파악하지 못하는 상태를 예제로 넣고, 이를 stored procedure 와 기존 데이터
샘플링을 통하여 메타데이터가 증강되고, 비로소 그 메타정보에 의해 적절한 온톨로지에 필요한 테이블이
찾아지고, text2sql 에 의하여 만들어진 sql 에 의하여 온톨로지 객체화가 이뤄지는 과정"*

---

## 관계

이 스펙은 **새 기능을 발명하지 않는다.** [001](../001-datasource-backed-virtual-classes/spec.md)·
[002](../002-catalog-driven-ontology/spec.md)·[003](../003-ontology-build-strategies/spec.md) 이
만든 온톨로지 구축 경로와, [007](../007-skill-based-text2sql-and-analyzer/spec.md) 이 옮기는 중인
임베딩·색인을 **하나의 시나리오로 잇고, 그 시나리오가 실제로 성립하는지 처음으로 검증한다.**

003 이 정의한 전략1(문서+데이터소스 → 역바인딩)이 이 스펙의 무대다. 003 FR-006 은 판정 근거를
**세 가지**로 규정했는데 — 이름 유사도, 속성↔컬럼 겹침, **샘플 값 형태 일치** — 셋째가 구현되지
않았다. 이 스펙은 그 미구현 신호가 **없으면 시나리오가 성립하지 않는 조건**을 만든다.

007 과는 공급-소비 관계다. 007 이 메타데이터 증강 단계에서 임베딩을 만들고, 이 스펙이 그것을
**온톨로지 구축에서 처음으로 소비한다.** 007 §"data-fabric 에 임베딩 코드가 0건" 이 참인 동안
이 스펙의 US3 은 통과할 수 없다.

## 배경 — 지금 예제는 문제를 숨긴다

### 확인된 사실

번들된 manufacturing 예제는 메타데이터가 **이미 완성돼 있다.**

| 항목 | 실측 | 확인 경로 |
|---|---|---|
| 테이블 | 13개, 전부 `mfg_product` 꼴 의미 노출 이름 | `ontology-studio/desktop/resources/backend/seed/postgres/01_ddl_schema.sql` |
| 컬럼 | 158개, 전부 `product_name` 꼴 | 같은 파일 |
| 외래키 | 12개 전부 선언됨 | `grep -c "FOREIGN KEY"` |
| 주석 | 컬럼마다 한글 설명 | 같은 파일 |

그래서 두 가지가 보이지 않는다.

**첫째, 메타데이터 증강이 무엇을 보태는지 보이지 않는다.** 증강 전에 이미 `product_name` 이라고
쓰여 있으면, 증강이 "제품명"이라고 덧붙여도 새로 얻은 것이 없다.

**둘째, 테이블 선택이 이름만으로 풀린다.** 전략1의 채점식이 그렇게 생겼다.

↳ `ontology-studio/backend/src/modules/ontology/entity_matcher.py:27-29`

```
WEIGHT_COLUMN = 0.6   # 엔티티 속성명 ↔ 테이블 컬럼명 (정규화 후 완전일치)
WEIGHT_TYPE   = 0.2   # 일치한 것들의 타입 합의 비율
WEIGHT_NAME   = 0.2   # 엔티티명 ↔ 테이블명 토큰 자카드
```

판정 임계 (`entity_matcher.py:207-216`): `top < 0.40` → `no_match`,
`top >= 0.70 AND (top - runner_up) >= 0.15` → `auto`, 나머지 → `needs_review`.

이름을 코드로 바꾸면 세 신호가 **모두** 0 이 된다. 컬럼명 완전일치와 이름 자카드가 0 이 되는 것은
바로 보이지만, 타입 신호도 함께 죽는다 — `type_score` 는 *일치한 컬럼들 중의* 합의 비율
(`type_agreements / matched`)이라 **일치가 0이면 분자도 분모도 0**이다. 총점은 0.2 가 아니라
**정확히 0.0** 이다.

**실측으로 확인했다 (2026-08-05):** 목표 개념 13개 전부 `no_match`, 최고점 **0.000**, 자동 바인딩
**0건**. 우연이 아니라 산술이다.
↳ [`docs/business/evidence/17-spec008-baseline/`](../../docs/business/evidence/17-spec008-baseline/README.md)

### 증강 결과는 지금 채점에 들어가지 않는다

이것이 이 스펙의 진짜 과제다. 난독화는 문제를 **드러내기만** 한다.

- `entity_matcher.score_table` (`entity_matcher.py:115`) 이 참조하는 필드는 `table["name"]`,
  `table["columns"][].name`, `.type` 뿐이다. **`description` 을 읽지 않는다.**
- `schema_ontology.read_catalog` (`schema_ontology.py:111-128`) 는 `Table.description` 과
  `Column.description` 을 애써 읽어 오지만, 그 값은 생성된 클래스·속성의 **설명으로만** 실리고
  채점에는 한 톨도 반영되지 않는다.
- text2sql 이 만드는 증강 산출물(`Table.text_to_sql_vector`,
  `text_to_sql_embedding_text`, `text_to_sql_table_profile`)을 참조하는 ontology-studio 코드는
  **0건**이다.
- 온톨로지 구축 경로에 **벡터 검색이 없다.** 기존 인덱스 `entity_embedding_vector`,
  `chunk_embedding_vector` 는 `(:_Entity)` / `(:Chunk)` 대상이고 답변 모드 도구에만 노출된다.

domain-layer 쪽도 같은 병이다. `DataSourceLinker._calculate_name_similarity` 와
`schema_extractor._determine_layer` 의 `LAYER_PATTERNS` 는 **둘 다 테이블 이름 문자열**에 기댄다.

> **따라서 이 스펙은 예제 교체가 아니다.** 예제 교체는 절반이고, 나머지 절반은
> **증강된 메타데이터를 실제로 소비하는 경로를 처음 만드는 일**이다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 의미를 알 수 없는 데이터소스를 마주한다 (Priority: P1)

사용자가 설치본을 열고 번들된 레거시 예제를 데이터소스로 등록한다. 스키마를 열어 보면 테이블은
`TB01`…`TB13`, 컬럼은 `C001`…, 외래키는 하나도 없고 주석도 없다. 이 상태로 온톨로지 구축을 시도하면
**어떤 테이블도 자동으로 선택되지 않는다.** 시스템은 실패를 조용히 넘기지 않고, 왜 못 골랐는지
(이름과 컬럼명에서 얻은 신호가 없음) 사용자에게 알린다.

**Why this priority**: 이후 모든 이야기의 출발점이자 대조군이다. 이 상태가 재현되지 않으면
"증강이 효과가 있었다"를 주장할 근거가 없다. 이 스토리만 구현해도 **"증강 없이는 안 된다"는
사실을 보여주는 데모**로서 독립적 가치가 있다.

**Independent Test**: 설치본에서 레거시 예제를 등록 → 온톨로지 구축(전략1) 실행 → 모든 엔티티가
`no_match` 로 보고되고, 자동 바인딩이 0건임을 확인.

**Acceptance Scenarios**:

1. **Given** 레거시 예제가 등록되고 증강이 실행되지 않은 상태, **When** 사용자가 스키마를 조회하면,
   **Then** 테이블·컬럼 이름은 코드이고 외래키와 설명은 비어 있다.
2. **Given** 같은 상태, **When** 전략1 역바인딩 미리보기를 실행하면, **Then** 모든 엔티티의 판정이
   `no_match` 이고 자동 바인딩 대상이 0건이다.
3. **Given** 같은 상태, **When** 사용자가 자연어로 질의하면, **Then** 시스템은 근거 부족을 이유로
   답을 지어내지 않고 증강이 필요함을 안내한다.

### User Story 2 - 코드와 데이터에서 의미를 복원한다 (Priority: P1)

사용자가 「메타데이터 증강」에서 번들된 프로시저 디렉터리를 그대로 두고 「분석 시작」을 누른다.
시스템은 스토어드 프로시저의 로직·주석·지역 변수명과 실제 데이터 값 샘플을 근거로, 각 테이블과
컬럼이 무엇인지 설명을 만들어 카탈로그에 채운다. 선언되지 않은 테이블 간 관계도 프로시저의
조인 조건에서 추론한다.

**Why this priority**: 이 스펙의 핵심 주장 — "의미는 이름이 아니라 코드와 데이터에 있다" — 이
성립하는 지점이다. US1 과 함께 있어야 전후 비교가 된다.

**Independent Test**: 증강 실행 전후로 카탈로그의 설명 채움률과 추론된 관계 수를 비교.

**Acceptance Scenarios**:

1. **Given** US1 의 상태, **When** 증강을 실행하면, **Then** 테이블과 컬럼에 설명이 채워진다.
2. **Given** 증강이 끝난 상태, **When** 사용자가 어떤 컬럼의 근거를 물으면, **Then** 그 설명이
   어느 프로시저 / 어떤 데이터 관찰에서 나왔는지 추적할 수 있다.
3. **Given** 프로시저에 조인 조건이 있는 테이블 쌍, **When** 증강이 끝나면, **Then** 그 관계가
   추론된 관계로 기록되고 **선언된 외래키가 아니라 추론임이 구별된다.**
4. **Given** 증강이 끝난 상태, **When** 정답지와 대조하면, **Then** 복원 성과가 수치로 나온다.

---

### User Story 3 - 증강된 메타데이터로 필요한 테이블이 찾아진다 (Priority: P1)

사용자가 온톨로지를 구축한다. 시스템은 이름이 아니라 **증강된 설명과 데이터 특성**을 근거로,
각 온톨로지 개념에 맞는 테이블을 찾아 제시한다. 각 후보에는 왜 그 테이블인지 근거가 붙는다.
확신이 부족하면 자동으로 바인딩하지 않고 사람에게 넘긴다.

**Why this priority**: 사용자가 요청한 *"알아서 적절한 테이블 소스를 증강된 메타데이터를 기반으로
찾아오고"* 가 바로 이것이다. US1·US2 가 만든 조건 위에서만 의미가 있다.

**Independent Test**: 같은 온톨로지·같은 데이터소스에 대해 증강 전(US1)과 증강 후의 바인딩 결과를
정답지와 대조.

**Acceptance Scenarios**:

1. **Given** 증강이 끝난 레거시 예제, **When** 전략1 역바인딩을 실행하면, **Then** 목표 개념들이
   정답 테이블에 바인딩된다.
2. **Given** 같은 상태, **When** 사용자가 후보 목록을 보면, **Then** 각 후보에 선택 근거가 제시된다.
3. **Given** 두 개념이 같은 테이블을 지목하는 경우, **When** 판정하면, **Then** 충돌로 보고하고
   자동 바인딩하지 않는다.
4. **Given** 증강되지 않은 테이블이 섞여 있는 경우, **When** 판정하면, **Then** 근거 부족으로
   자동 바인딩하지 않는다.

### User Story 4 - 질의 결과가 온톨로지 객체가 된다 (Priority: P2)

사용자가 자연어로 묻는다. 시스템이 SQL 을 만들어 실행하고, 사용자는 그 결과를 온톨로지 객체로
등록한다. 등록된 객체는 이후 온톨로지 탐색에서 일반 객체처럼 다뤄지고, 어떤 질문·어떤 SQL 에서
나왔는지 추적할 수 있다.

**Why this priority**: 사용자가 요청한 *"text2sql 에 의하여 만들어진 sql 에 의하여 온톨로지
객체화"* 다. US3 까지가 성립해야 의미 있는 SQL 이 나오므로 뒤에 둔다.

**Independent Test**: 자연어 질의 → 결과 확인 → 객체화 → 온톨로지에서 그 객체 조회.

**Acceptance Scenarios**:

1. **Given** US3 이 끝난 상태, **When** 사용자가 자연어로 묻고 결과를 객체화하면, **Then** 결과 행이
   온톨로지 객체로 등록된다.
2. **Given** 객체화된 결과, **When** 사용자가 출처를 확인하면, **Then** 원 질문과 실행된 SQL 을 볼 수 있다.
3. **Given** 같은 질의를 다시 객체화하면, **Then** 중복 객체가 쌓이지 않는다.
4. **Given** 데이터소스에 바인딩된 **가상** 클래스, **When** 객체화를 시도하면, **Then** 시스템은
   이를 거부한다 — 가상 클래스는 인스턴스를 저장하지 않는다(spec 001 SC-001).

### Edge Cases

- 프로시저가 참조하지 않는 테이블은 증강할 근거가 없다. 이때 설명이 비는 것이 정상이며, 시스템은
  이를 **실패가 아니라 "근거 없음"** 으로 구분해 보고해야 한다.
- 프로시저 코드가 잘못된 의미를 시사할 수 있다(오래된 주석, 죽은 코드). 증강 결과는 **주장이지
  사실이 아니며**, 근거를 함께 남겨 사람이 반박할 수 있어야 한다.
- 데이터 샘플이 편향될 수 있다(테스트 데이터, 전부 NULL 인 컬럼). 샘플만으로 단정하지 않는다.
- 두 테이블의 컬럼 구성이 거의 같으면(예: 일별 집계 테이블들) 증강 후에도 변별이 어렵다.
  이때는 자동 바인딩하지 않고 사람에게 넘긴다.
- 증강을 두 번 실행하면 설명이 덮어써지는가 누적되는가 — 재실행이 이전 결과를 훼손하지 않아야 한다.
- 난독화된 예제와 기존 깨끗한 예제가 같은 그래프에 공존할 때 서로를 침범하지 않아야 한다.
- 임베딩 설정이 없는 상태에서 증강을 실행하면 — 007 이 임베딩을 필수로 규정했으므로 시스템은
  진행 전에 설정을 요구해야 한다.

## Requirements *(mandatory)*

> ### 2026-08-05 실측 — 격차가 예상보다 한 단계 아래였다
>
> 난독화 예제를 실제로 돌려 보고 알아낸 것들. 추정이 아니라 관측이다.
>
> 1. **분석기가 카탈로그 라벨에 함께 쓰고 있었다.** `nodes/table.py` 의 `SET t:Table` 때문에
>    매 run 의 wipe 가 **카탈로그를 함께 지웠다** — `legacy` 를 분석하자 `manufacturing` 의
>    `:Table` 11개가 0이 됐다. 이중 라벨을 걷어내고 설명은 **투영**으로 옮겼다
>    (`catalog_projection.py`). 고친 뒤 카탈로그 13테이블·158컬럼이 분석 run 을 통과해 생존했다.
> 2. **테이블·컬럼 설명이 DDL 주석 복사였다.** 깨끗한 예제의 "제품 마스터 (Product Master)" 는
>    코드 분석 산출이 아니었다. 주석을 지우자 산출이 **0건**이 됐다.
> 3. **scan 단계도 이름에 의존한다.** `framework` 전략에서 scan 에이전트가 없는 `**/*.java` 를
>    반복 탐색하다 LLM 호출 한도(30)를 소진하고 **run 자체가 실패**했다. 테이블 분석에 닿기도
>    전이다. DDL+프로시저 프로젝트에는 `dbms` 전략이 맞다.
> 4. **파서의 파싱은 업로드와 별도 호출이다.** `/antlr/fileUpload` 는 파일만 받고,
>    `/antlr/parsing` 을 불러야 AST JSON 이 생긴다. AST 가 없으면 `functions` 가 비어
>    설명 생성 단계가 **조용히 건너뛴다**(`reason: no functions`).
> 5. **파서 상태는 재시작을 넘기지 못한다.** 컨테이너가 다시 만들어지면 반입 파일과 AST 가
>    사라진다.
>
> **이름 축이 셋으로 갈려 있었다** — 분석기의 `datasource` 는 폴더명, 카탈로그의 것은 등록된
> 데이터소스명이다. 데스크톱이 이미 *"폴더 이름이 곧 그래프의 이름"* 을 규칙으로 두었으므로,
> 레거시 예제를 **자기 데이터소스로 등록**해 폴더=프로젝트=데이터소스=스키마를 한 이름으로 맞췄다.
> 덕분에 두 예제의 분리(FR-033b)가 스키마가 아니라 **데이터소스 수준**이 되어 더 강해졌다.

- **FR-008a**: 증강 파이프라인은 **이름이 의미를 주지 않는 입력에서도 완주해야 한다.**
  프로젝트 식별에 실패하더라도 탐색을 무한히 반복하지 않고 실패를 실패로 보고해야 한다.
- **FR-008b**: 분석기는 **카탈로그 라벨에 직접 쓰지 않는다.** 알아낸 설명은 기존 카탈로그 노드에
  투영한다. 그래야 분석기의 wipe 가 카탈로그를 지우지 않는다.
- **FR-008c**: 인제스천은 **파싱까지 한 흐름**이어야 한다. 업로드만 하고 파싱을 부르지 않으면
  AST 가 없고, 그러면 설명 생성이 조용히 건너뛰어 "증강했는데 아무것도 안 나온다"가 된다.

### 예제 데이터 (FR-001 ~ FR-008)

- **FR-001**: 시스템은 **의미를 드러내지 않는 이름**을 가진 예제 데이터소스를 번들해야 한다.
  테이블명과 컬럼명은 업무 의미를 유추할 수 없는 코드여야 한다.
- **FR-002**: 그 예제에는 **선언된 외래키가 없어야 한다.**
- **FR-003**: 그 예제의 스키마 정의에는 **의미를 알려주는 주석이 없어야 한다.**
- **FR-004**: 그 예제의 **데이터 값은 원본 그대로**여야 한다. 값은 증강의 근거이므로 난독화 대상이
  아니다.
- **FR-005**: 그 예제에는 **의미를 담은 스토어드 프로시저**가 포함되어야 한다. 프로시저의 이름·주석·
  지역 변수명·로직은 난독화하지 않는다 — 레거시에서 의미가 남아 있는 자리가 여기다.
- **FR-006**: 난독화된 예제는 **원본과 이름 매핑으로부터 생성**되어야 한다. 난독화 결과물을 직접
  작성해 두지 않는다.
  - *이유*: 매핑이 없으면 "무엇이 정답인가"가 사라져 증강 품질을 사람 눈으로만 볼 수 있다.
    생성 방식은 매핑 파일이 곧 **정답지**가 되어 자동 채점을 가능하게 한다.
- **FR-007**: 이름 매핑에는 원래 이름과 **업무 의미 레이블**이 함께 있어야 한다. 채점은 이름 복원이
  아니라 **의미 일치**로 하기 때문이다.
- **FR-008**: **인제스천 입력과 실제 조회 대상 데이터베이스가 같은 이름 체계**를 써야 한다.
  - *이유*: 한쪽만 난독화하면 질의는 깨끗한 스키마를 보고 온톨로지는 난독화된 카탈로그를 보게 되어
    시나리오가 성립하지 않는다.

### 메타데이터 증강 (FR-009 ~ FR-015)

- **FR-009**: 시스템은 **스토어드 프로시저 코드**를 근거로 테이블·컬럼의 설명을 만들어야 한다.
- **FR-010**: 시스템은 **실제 데이터 값 샘플**을 근거로 컬럼의 성격을 보강해야 한다.
- **FR-011**: 시스템은 프로시저의 조인 조건에서 **테이블 간 관계를 추론**해야 한다.
- **FR-012**: 추론된 관계는 **선언된 외래키와 구별**되어야 한다.
- **FR-013**: 각 증강 결과에는 **근거**(어느 프로시저의 어느 부분, 어떤 데이터 관찰)가 남아야 한다.
- **FR-014**: 근거가 없는 테이블·컬럼은 **추측으로 채우지 않고** "근거 없음"으로 남겨야 한다.
- **FR-015**: 증강을 다시 실행해도 **이전 결과가 훼손되지 않아야** 한다.

### 테이블 자동 발견 (FR-016 ~ FR-022)

- **FR-016**: 온톨로지 구축의 테이블 선택은 **증강된 메타데이터를 근거로 사용해야 한다.**
  - *현재 상태*: 사용하지 않는다. 채점은 이름·컬럼명 문자열과 타입뿐이다
    (`entity_matcher.py:115-164`).
- **FR-017**: 이름 신호가 전혀 없는 상태에서도 **올바른 테이블을 찾을 수 있어야 한다.**
- **FR-018**: 각 후보에는 **왜 그 테이블인지 근거**가 제시되어야 한다.
- **FR-019**: 확신이 임계에 못 미치면 **자동 바인딩하지 않고** 사람에게 넘겨야 한다.
- **FR-020**: 두 개념이 같은 테이블을 지목하면 **충돌로 보고**하고 자동 바인딩하지 않아야 한다.
- **FR-021**: 증강 전/후의 판정 결과를 **같은 척도로 비교**할 수 있어야 한다.
- **FR-022**: 003 FR-006 이 규정한 **샘플 값 형태 일치** 신호가 판정에 반영되어야 한다.
  - *현재 상태*: 미구현. `sample_rows` 는 존재하나 채점기가 호출하지 않는다.

### 온톨로지 객체화 (FR-023 ~ FR-028)

- **FR-023**: 사용자는 자연어 질의 결과를 **온톨로지 객체로 등록**할 수 있어야 한다.
- **FR-024**: 등록된 객체에는 **원 질문과 실행된 SQL** 이 출처로 남아야 한다.
- **FR-025**: 같은 질의를 다시 객체화해도 **중복이 쌓이지 않아야** 한다.
- **FR-026**: **가상 클래스에는 객체화를 허용하지 않아야** 한다 (spec 001 SC-001: 저장 인스턴스 0건).
- **FR-027**: 객체화된 결과는 온톨로지 탐색에서 **다른 객체와 동일하게 다뤄져야** 한다.
- **FR-028**: 객체화는 **domain-layer 가 수행**한다 (결정 Q1-B). 따라서 온톨로지 쓰기 주체가 둘이
  되므로, **두 주체가 각각 무엇을 쓰는지 경계가 문서로 확정**되어야 한다. 경계가 없으면 같은 노드를
  두 서비스가 덮어쓴다.
- **FR-028a**: 이 경계는 **헌법에 반영**되어야 한다. 현재 헌법은 *"온톨로지 쓰기는 ontology-studio
  가 단독으로 갖는다"* 고 규정하므로, 개정 없이 구현하면 코드가 헌법을 위반한 상태가 된다.
  헌법 개정은 이 스펙의 **산출물**이지 부수 효과가 아니다.

### domain-layer 번들 편입 (FR-034 ~ FR-040)

결정 Q1-B 의 결과다. 아래는 **조사에서 확인된 실제 제약**이며, 하나라도 빠지면 번들이 서지 않거나
조용히 잘못 동작한다.

- **FR-034**: domain-layer 가 **데스크톱 설치본에서 기동**되어야 한다. 현재 번들은 domain-layer 를
  전혀 참조하지 않는다(컨테이너 7개: neo4j·mindsdb·postgres·mysql·antlr·data-fabric·text2sql).
- **FR-035**: **포트가 한 값으로 정리**되어야 한다. 현재 코드 기본값 `8002`, 운영 규약 `8001`,
  Dockerfile `EXPOSE 8002` 로 세 곳이 어긋나 있다. 어긋난 채로 두면 호출자가 어느 것을 믿을지
  알 수 없다.
- **FR-036**: domain-layer 가 붙는 **데이터베이스가 설치본의 것으로 설정**되어야 한다. 객체화
  경로의 기본 데이터베이스가 `meetingroom` 으로 되어 있어, 그대로 두면 엉뚱한 곳에 붙는다.
- **FR-037**: 온톨로지 스키마 저장이 **전체 재작성** 방식이므로(저장 시 기존 노드를 지우고 다시
  만든다), 동시 실행으로 서로의 결과를 지우지 않도록 **보호**되어야 한다.
- **FR-038**: domain-layer 편입 후에도 **기존 7개 서비스의 동작이 회귀하지 않아야** 한다.
- **FR-039**: 편입에 따른 **메모리 증가분이 측정되어 기록**되어야 한다. 현재 유휴 실측이
  **7.3 GiB**(podman VM 6.02 + Electron 0.56 + 호스트 파이썬 0.73, 2026-08-05)이고, 사업 목표는
  권장 16 GB / 최소 8 GB 다. **최소 8 GB 목표는 이미 현재 기본 설정으로 성립하지 않으므로**,
  이 편입은 그 격차를 더 벌린다. 증가분과 대응책이 함께 기록되어야 한다.
- **FR-040**: domain-layer 가 이름 문자열에 기대는 두 경로 — 노드↔테이블 자동 매핑의 이름 유사도와,
  테이블명 패턴으로 레이어를 정하는 로직 — 도 **증강된 메타데이터를 근거로 사용해야 한다**.
  난독화된 예제에서는 둘 다 무너지므로(§배경), 편입만 하고 두면 매뉴얼 9장이 동작하지 않는다.

### 시나리오 성립 (FR-029 ~ FR-033)

- **FR-029**: 설치본은 이 시나리오를 **처음부터 끝까지 실행할 수 있어야** 한다.
- **FR-030**: 「메타데이터 증강」을 열면 번들 예제 위치가 **기본 선택**되어 있어야 한다.
- **FR-031**: 각 단계는 **앞 단계의 결과에 의존함이 사용자에게 보여야** 한다. 증강 없이 구축을
  시도하면 왜 안 되는지 알려야 한다.
- **FR-032**: 시나리오 실행이 **기존에 등록된 데이터를 지우지 않아야** 한다 (헌법 원칙 IV).
- **FR-033**: 이 시나리오는 **매뉴얼과 일치**해야 한다. 예제를 바꾸면 매뉴얼의 해당 장을 함께 고친다.
- **FR-033a**: 설치본은 **난독화 예제를 기본**으로 제공하되, **깨끗한 예제도 선택**할 수 있어야
  한다 (결정 Q2-C). 매뉴얼 3·4·5장을 그대로 재현할 수 있어야 하기 때문이다.
- **FR-033b**: 두 예제는 **같은 그래프에서 서로를 침범하지 않아야** 한다. 한쪽을 쓰는 동안 다른
  쪽의 카탈로그·증강 결과가 훼손되면 안 된다.

### Key Entities

- **이름 매핑 (정답지)**: 난독화 이름 ↔ 원래 이름 ↔ 업무 의미 레이블. 난독화본 생성의 입력이자
  증강 품질 채점의 기준.
- **난독화 예제 데이터소스**: 코드 이름 테이블·컬럼, 외래키 없음, 주석 없음, 원본 값 유지.
- **증강된 설명**: 테이블·컬럼에 붙는 업무 의미. 근거(출처 코드 위치, 데이터 관찰)를 동반.
- **추론된 관계**: 프로시저 조인에서 도출한 테이블 간 연결. 선언된 외래키와 구별됨.
- **바인딩 판정**: 개념 ↔ 테이블 후보와 점수·근거·판정(자동/검토필요/충돌/없음).
- **온톨로지 객체**: 질의 결과에서 만들어진 인스턴스. 원 질문과 SQL 을 출처로 보유.

했다. domain-layer 에는 이미 `POST /ontology/instances/bulk-create` 가 있어 SQL 을 받아
`(:OntologyInstance)` 를 만들고 `HAS_INSTANCE` 로 붙인다.

**충돌**: 헌법은 *"온톨로지 쓰기는 ontology-studio 가 단독으로 갖는다"* 고 규정하고, domain-layer
에는 무상태 `POST /whatif/analyze-matrix` 만 위임한다.

| | 선택지 | 함의 |
|---|---|---|
| A | ontology-studio 의 기존 적재 경로에 "SQL 결과" 입력을 추가 | 헌법 유지. materialized 클래스 경로 재사용. domain-layer 번들 불필요 → 메모리 증가 없음. 기존 코드를 복제하지 않음 |
| B | domain-layer 를 번들에 편입하고 그 엔드포인트를 사용 | 매뉴얼 6·7·9장(ObjectType·온톨로지 구성·데이터소스 매핑)이 함께 들어옴. **헌법 개정 필요.** 포트 불일치(코드 8002 / 규약 8001 / Dockerfile 8002), 기본 DB `meetingroom`, 스키마 저장이 전체 재작성이라 동시 실행 취약. 실측 7.3 GiB 위에 메모리 추가 |
| C | 둘 다 — 지금은 A, 매뉴얼 6~12장 확장 때 B | 범위가 커지고 쓰기 주체가 둘이 되는 시점이 생김 |

**결정: B.** (제 권고는 A 였다. 헌법 유지와 메모리를 근거로 들었지만, 사용자가 B 를 택했다 —
매뉴얼 6·7·9장 기능을 실제로 갖는 쪽의 가치가 그 비용보다 크다는 판단이다.)

**B 를 택했으므로 반드시 따라오는 것들** — FR-028a, FR-034~040 이 이를 요구사항으로 고정한다:

1. **헌법 개정이 산출물이 된다.** 쓰기 주체가 둘이 되므로 경계를 헌법에 새로 써야 한다.
   개정 없이 구현하면 코드가 헌법 위반 상태로 남는다.
2. **포트 세 곳의 불일치를 먼저 정리해야 한다** (코드 8002 / 규약 8001 / Dockerfile 8002).
3. **기본 데이터베이스 `meetingroom` 을 설치본의 것으로 바꿔야 한다.**
4. **스키마 저장의 전체 재작성**을 동시 실행으로부터 보호해야 한다.
5. **메모리 목표와 정면으로 부딪힌다.** 유휴 실측 7.3 GiB 는 이미 "최소 8 GB" 를 충족하지 못한다.
   증가분과 대응책(예: VM 정원 축소 — 실측상 컨테이너 실수요는 2.80 GiB, VM 정원 6 GiB 는 설정값)을
   함께 기록해야 한다.
6. **domain-layer 자신의 이름 기반 매칭도 고쳐야 한다** (FR-040). 안 고치면 난독화 예제에서
   매뉴얼 9장이 동작하지 않는다 — 편입의 목적이 사라진다.

### Q2 — 기존 깨끗한 예제를 어떻게 할 것인가 → **C. 난독화본 기본 + 깨끗한 예제 선택 유지**

**맥락**: FR-008 은 인제스천 입력과 실제 조회 대상 DB 가 같은 이름 체계를 쓸 것을 요구한다.
그런데 실제 조회 대상 DB 를 난독화하면 **매뉴얼 3·4·5장의 화면·예시 질의·결과가 전부 어긋난다**
(예: 5장의 *"제품 카테고리별 총 매출액…"* 이 `mfg_product` 를 전제한다).

| | 선택지 | 함의 |
|---|---|---|
| A | 기존 manufacturing 을 난독화본으로 **전면 전환** | 사용자 지시(*"예제로 전환"*)에 가장 충실. 매뉴얼 3·4·5장 개정 필요. 기존 증거 자료(스크린샷)도 무효화 |
| B | 난독화된 **별도 스키마를 추가**하고 manufacturing 은 유지 | 매뉴얼 무손상. 두 예제 비교로 학습 효과. 샘플 DB 용량·기동 시간 증가. "전환"이라는 지시와는 다름 |
| C | 난독화본을 **기본**으로 하고 깨끗한 예제는 선택 항목으로 유지 | A 의 효과 + 매뉴얼 재현 가능. 설정 하나가 늘어남 |

**결정: C.** (권고와 일치.) 첫 실행에서 레거시 시나리오를 만나되, 매뉴얼 3·4·5장을 그대로 재현할
수 있다. 대가는 **유지 대상이 둘**이라는 것이다 — FR-033a·FR-033b 가 이를 요구사항으로 고정한다.
두 예제가 같은 그래프에서 서로를 침범하지 않는지가 이 선택의 실패 지점이다.

## Assumptions

- **난독화 강도**: 테이블 `TB01`…, 컬럼 `C001`… 같은 완전 무의미 코드를 쓴다. 사용자가 *"코드로
  되어있어 의미를 파악하지 못하는 상태"* 라고 명시했다.
- **프로시저는 난독화하지 않는다** (FR-005). 프로시저 이름·주석·지역 변수명은 그대로 두고
  테이블·컬럼 참조만 코드로 바꾼다. 레거시 현실에 부합하고, 증강의 근거가 남아야 하기 때문이다.
- **데이터 값은 그대로 둔다** (FR-004). 값이 두 번째 증강 근거이므로 난독화하면 시나리오가 성립하지
  않는다.
- **채점은 이름 복원이 아니라 의미 일치로 한다** (FR-007). 증강이 `product_id` 라는 문자열을
  되살릴 이유가 없다 — "제품 식별자"면 충분하다.
- **임베딩은 007 에 의존한다.** 007 이 메타데이터 증강 단계에서 임베딩을 만들지 않으면 US3 의
  의미 기반 탐색은 설명 텍스트만으로 동작해야 한다. 007 T1~T4 가 이미 구현됐다는 전제를 둔다.
- **증강 품질은 LLM 에 의존하므로 결과가 결정적이지 않다.** SC-002 는 단일 실행이 아니라 반복
  실행의 결과로 보고한다.
- **분석기의 전역 삭제는 이미 수정됐다** (2026-08-05, `robo-data-analyzer/shared/neo4j/
  schema_constraints.py`). FR-032/SC-007 은 그 수정 위에서만 성립한다. 실제 인제스천으로
  데이터소스가 보존되는지는 **아직 실증되지 않았다.**
- **범위 밖**: 매뉴얼 8·10·11·12장(BPMN·원인분석·What-if·감시 에이전트)은 다루지 않는다.
