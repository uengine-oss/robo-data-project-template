## R1 — 난독화 SQL 재작성을 어떻게 안전하게 하는가

**결정**: 식별자 인지형 재작성기를 쓴다. 문자열 리터럴과 주석은 건너뛰고, **긴 이름부터**
치환한다.

**근거**: DML 형식이 단순하고 규칙적이다.

```sql
INSERT INTO manufacturing.mfg_product (product_id, product_name, product_category, ...) VALUES
('PROD-001', '고정밀 베어링 A형', '자동차부품', 45000.00, ...),
```

↳ `ontology-studio/desktop/resources/backend/seed/postgres/02_dml_master_data.sql`

두 가지가 위험하다.

1. **문자열 값 안의 이름.** 값에 `'product_id'` 같은 문자열이 있으면 순진한 치환이 데이터를
   바꾼다. FR-004 는 값을 원본 그대로 두라고 요구하므로 이는 명백한 오류가 된다.
   → 작은 렉서로 `'...'`(`''` 이스케이프 포함)와 `--` / `/* */` 를 건너뛴다.
2. **접두사 겹침.** `product_id` 를 먼저 치환하면 `mfg_product` 안의 `product` 가 이미
   바뀐 뒤라 매칭이 깨진다. → **길이 내림차순**으로 치환하고 단어 경계를 요구한다.

**대안 기각**:
- `sed`/정규식 일괄 치환 — 위 1·2 를 다룰 수 없다. 4.9 MB 를 눈으로 검증할 수 없으므로
  "아마 괜찮다"로 넘길 수 없다.
- PostgreSQL 파서(`pglast` 등) 사용 — 정확하지만 의존성이 늘고, Oracle 방언 프로시저
  (`tutorial/.../procedures/*.sql`)는 파싱하지 못한다. 프로시저까지 같은 도구로 다뤄야 한다.

**검증 방법**: 생성 후 (a) 원본과 생성본의 **토큰 수·INSERT 문 수·VALUES 튜플 수**가 같고,
(b) 실제로 DB 를 세워 **테이블별 행 수**가 원본과 일치하는지 확인한다. 행 수 비교가 최종
관문이다 — 값이 깨졌으면 적재가 실패하거나 수가 달라진다.

## R2 — 증강 신호를 채점에 어떻게 넣는가 (결정성 유지)

**결정**: `entity_matcher` 는 **결정적으로 유지**한다. 증강 신호는 두 가지 형태로만 넣는다.

1. **증강된 설명 텍스트의 토큰 겹침** — 기존 이름 토큰 자카드와 같은 계산을 `description` 에도
   적용. 결정적이다.
2. **샘플 값 형태 일치** — 003 FR-006 이 규정했으나 미구현인 신호. 값의 *형태*(날짜꼴, 코드꼴,
   범주 카디널리티, 수치 범위)를 비교한다. 값 자체가 아니라 형태이므로 결정적이다.

임베딩 유사도는 **채점에 넣지 않고** 후보 축소(pre-filter)로 분리한다.

**근거**: `entity_matcher.py:18-19` 의 모듈 docstring 이 *"Nothing here calls an LLM, so the
same inputs always produce the same ranking"* 를 성질로 못박고 있다. 헌법의 ontology-studio
절도 *"테이블 구조 → 온톨로지 경로는 결정적이다 (LLM 금지)"* 를 요구한다.

임베딩은 원격 모델 호출이라 **같은 입력이 같은 벡터를 준다는 보장이 약하다**(모델 버전 변경,
서비스 측 변경). 그것을 점수에 섞으면 "같은 카탈로그는 같은 온톨로지"라는 성질이 조용히
깨지고, 그 사실은 한참 뒤에나 드러난다.

**대안 기각**:
- **임베딩을 주 신호로** — 결정성을 잃는다. 또 spec 007 이 아직 진행 중이라 증강 단계에서
  벡터가 생긴다는 보장이 없다(007 §"data-fabric 에 임베딩 코드가 0건"). 이 스펙이 007 의
  미완성에 직접 매달리게 된다.
- **LLM 심판을 채점기에** — 위와 같은 이유 + 비용·재현성.

**후보 축소로 분리하는 이유**: 임베딩이 있으면 후보를 줄여 속도를 얻고, 없으면 전수 채점으로
폴백한다. **결과의 정확성은 임베딩 유무에 의존하지 않는다** — 축소는 성능 최적화이지 판정이
아니다. 축소 때문에 정답이 탈락하면 안 되므로, 축소 임계는 넉넉히 두고 축소로 탈락한 후보 수를
보고에 남긴다.

**미확인**: 증강된 설명만으로 SC-002 를 만족할 만큼 변별력이 나오는지는 **측정해야 안다.**
T3 기준선 → T4 측정이 이 질문의 답이다. 안 나오면 가중치가 아니라 **증강 품질**이 문제일 수
있으므로, T3 에서 채움률(SC-003)을 함께 재는 것이 진단 근거가 된다.

## R3 — 두 예제를 어떻게 공존시키는가

**결정**: 같은 PostgreSQL 안의 **별도 스키마**로 둔다. 난독화본이 기본 선택이다.

- 깨끗한 예제: 스키마 `manufacturing` (현행 유지)
- 난독화 예제: 스키마 `legacy`

**근거**: 헌법 원칙 II 가 *"테이블을 조회할 때 `(t.datasource = $ds OR t.db = $ds)` 를 항상 함께
쓴다"* 를 요구하고, `:Table` 제약이 `(db, schema, name)` 3-튜플이다. **스키마가 다르면 노드가
분리된다** — FR-033b(상호 비침범)가 그래프 수준에서 보장된다.

같은 스키마에 접두사만 다르게 두는 방식은 기각한다. 접두사는 **이름의 일부**라서, 난독화의
목적(이름에서 아무 신호도 나오지 않게 하기)과 충돌한다.

별도 데이터소스로 두는 방식도 기각한다. 데이터소스가 둘이면 사용자가 등록을 두 번 해야 하고,
"하나의 데이터소스 안에 여러 스키마"라는 실제 레거시 형태와 멀어진다.

**스키마 이름을 `legacy` 로 한 이유**: 업무 의미를 드러내지 않으면서 사람이 무엇인지 알 수 있다.
FR-001 이 금지하는 것은 **테이블·컬럼** 이름이 의미를 드러내는 것이다.

## R4 — domain-layer 포트·DB 정리

**결정**: 데스크톱 번들에서 domain-layer 를 **컨테이너로 띄우고 포트를 명시적으로 고정**한다.
호스트 노출 포트는 다른 서비스와 겹치지 않는 값으로 새로 정하고, 컨테이너 내부 포트는
Dockerfile 값(`8002`)에 맞춘다.

**근거 — 충돌이 3중이 아니라 4중이다**:

| 출처 | 값 | 확인 |
|---|---|---|
| 코드 기본값 | `8002` | `domain-layer/app/config.py:14` `PORT: int = 8002` |
| Dockerfile | `8002` | `domain-layer/Dockerfile:22` `EXPOSE 8002` |
| 운영 규약 | `8001` | `installation.md:430,437`, `.env.example:62` |
| **domain-layer 자신이 8001 에 다른 서비스를 기대** | `8001` = **PDF2BPMN** | `domain-layer/app/config.py:54` `PDF2BPMN_URL: str = "http://localhost:8001"` |

넷째가 결정적이다. **운영 규약대로 8001 에 domain-layer 를 띄우면, domain-layer 가 PDF2BPMN 을
부를 때 자기 자신을 호출한다.** 지금은 PDF2BPMN 경로를 안 쓰면 드러나지 않지만, 쓰는 순간
설명하기 어려운 증상이 된다.

컨테이너 안에서는 포트 충돌이 없으므로 내부 `8002` 를 그대로 두고, **호스트 노출만 새 값으로**
매핑하는 것이 변경을 가장 적게 만든다. 데스크톱은 이미 모든 서비스를 그렇게 다룬다.

**DB**: 객체화 경로가 붙는 기본 데이터베이스가 `meetingroom` 이다(`PG_DATABASE` 기본값).
설치본의 PostgreSQL 로 명시 설정한다 — 기본값에 기대지 않는다.

**미확인**: PDF2BPMN 을 실제로 쓰는 경로가 이번 시나리오에 포함되는지. 포함되지 않으면 넷째
충돌은 잠복 상태로 남는다 — 그래도 `.env` 에 명시해 두어야 다음 사람이 밟지 않는다.

## R5 — V-2: 번들이 들여오는 SQL 렌더링 패턴

**결정**: 편입 **전에** 이 경로를 점검하고, 사용자 입력이 닿으면 노출을 막거나 렌더링을
교체한다.

**확인된 사실**: `GET /ontology/ontology-nodes/{node_id}/data` 가 **HTTP 쿼리 파라미터**에서
`filter_*` 를 읽어 WHERE 절을 문자열로 조립한다.

↳ `domain-layer/app/routers/ontology.py:4600-4614`

```python
if re.match(r'^[a-zA-Z_][a-zA-Z0-9_]*$', col_name):   # 컬럼명은 가드됨
    safe_value = value.replace("'", "''")             # 값은 이스케이프 후 연결
    filter_conditions.append(f"{col_name} = '{safe_value}'")
```

컬럼명은 정규식으로 막혀 있다. 문제는 **값**이다.

`''` 이중화는 **PostgreSQL 표기 규칙을 전제한다.** 그런데 이 쿼리는 text2sql 의
`/text2sql/direct-sql` 을 거치고, 그 경로는 **MindsDB 로 갈 수 있다.** MindsDB 는 MySQL 방언이고
MySQL 은 기본적으로 **백슬래시를 이스케이프 문자로** 해석한다. 그 경우 `''` 이중화만으로는
문자열을 벗어나는 입력을 막지 못한다.

헌법이 이 패턴을 *"복사하지 않는다"* 고 판정했지만, **번들은 복사가 아니라 편입이라 그 판정을
비껴간다.** 이 스펙이 그 빈틈을 처음 밟는다.

헌법의 대안은 이미 정해져 있다 — ontology-studio 절: *"SQL 파라미터는 이스케이프하지 않고
타입으로 렌더한다"*, 위험 문자가 있으면 **거부**한다.

**미확인 — 실증 필요**: 이 경로가 실제로 MindsDB 로 라우팅되는지, 그리고 백슬래시를 포함한 값이
실제로 문자열을 벗어나는지는 **확인하지 않았다.** 추정으로 위험을 단정하지 않는다. T5 에서
실제 요청으로 확인하고, 확인될 때까지는 **해당 엔드포인트를 데스크톱 게이트웨이에 노출하지
않는다.** 노출하지 않는 것이 확인보다 싸다.

## R6 — 증강 품질을 어떻게 채점하는가

**결정**: 두 층으로 나눈다.

| 층 | 대상 | 방법 | 성격 |
|---|---|---|---|
| **1차 (객관)** | SC-001·SC-002·SC-004·SC-005 | 매핑 파일과 **기계적 대조** | 이진 판정, 재현 가능 |
| **2차 (해석)** | SC-003 설명 품질 | 채움률 + 의미 일치 표본 검토 | 사람/심판 필요 |

**근거**: SC-002("정답 테이블에 바인딩")는 **테이블 동일성**이라 기계 판정이 된다.
`legacy.TB06` 에 바인딩됐는가, 매핑상 그것이 `mfg_daily_sales` 인가 — 문자열 비교로 끝난다.

반면 SC-003("설명이 의미를 복원했는가")은 증강이 `"제품 식별자"` 라고 쓸지 `"제품 코드"` 라고
쓸지 알 수 없다. FR-007 이 매핑에 **업무 의미 레이블**을 함께 두라고 요구하는 이유다.

**1차만으로 스펙의 성패가 갈리도록 설계한다.** SC-001 과 SC-002 가 이 스펙의 존재 이유이고
둘 다 1차다. SC-003 은 진단 지표로 쓴다 — SC-002 가 낮을 때 *"채점기 문제인가 증강 품질
문제인가"* 를 가르는 데 필요하다.

**LLM 이 개입하므로 단일 실행으로 판정하지 않는다.** 반복 실행하고 결과를 분포로 보고한다.

## R7 — 메모리

**결정**: T5 에서 편입 전/후를 **같은 방법으로** 재고 증가분을 기록한다. 목표 미달이면
대응책을 함께 적되, **목표 자체의 조정은 사업 결정**으로 남긴다.

**기준선 (2026-08-05 실측, 유휴)**:

| 층 | 값 | 방법 |
|---|---|---|
| podman VM | 6.02 GiB | 호스트 프로세스 `com.apple.Virtualization.VirtualMachine` |
| Electron | 0.56 GiB | 메인 + GPU + 유틸 + 렌더러 RSS |
| 호스트 파이썬 | 0.73 GiB | analyzer 401 + backend 142 + catalog 109 + MCP 96 MB |
| **합계** | **7.31 GiB** | |

**측정 방법에 함정이 있다.** podman/vfkit 에서는 게스트 메모리가 **vfkit 프로세스에 잡히지
않는다**(vfkit phys_footprint 16 MB). 별도 VZ 헬퍼 프로세스에 잡히므로 그것을 봐야 한다.
같은 머신에 VM 이 셋 있어 오인하기 쉽다 — 16 GB 는 Docker Desktop, 1.9 GB 는 Claude 앱이다.

**대응 여지**: VM 정원 6 GiB 는 **설정값**(`ONTOLOGY_STUDIO_PODMAN_MEMORY`, 기본 `6144`)이고,
컨테이너 실수요는 **2.80 GiB** 다. 게스트가 정원을 거의 다 만졌고 VZ 가 반환하지 않으므로
호스트가 정원 전액을 낸다. 정원을 줄이면 호스트 비용이 직접 줄어든다.

**미확인**: 정원을 줄였을 때 Neo4j·MindsDB 가 견디는지. 부하 확인이 따로 필요하다.
