[001-datasource-backed-virtual-classes](../001-datasource-backed-virtual-classes/spec.md) 의
**대안 입구**다. 001 은 에이전트가 문서·의도·골든퀘스천을 읽고 온톨로지를 **설계**한다. 이
기능은 카탈로그에 이미 구조가 있을 때 그 설계 단계를 **건너뛴다**. 산출물(가상 클래스 +
바인딩)은 동일하므로 001 의 조회·행위·안전성 요구사항이 그대로 적용된다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 카탈로그가 아는 것을 다시 설계하지 않는다 (Priority: P1)

메타데이터가 추출된 스키마를 고르면, LLM 을 부르지 않고 테이블·컬럼·기본키·외래키에서 곧바로
클래스·속성·키·관계를 만든다. 같은 카탈로그는 항상 같은 온톨로지를 만든다.

**Why this priority**: 이 기능의 전부다. 구조가 이미 기계가 읽을 수 있는 형태로 있는데 LLM 에
다시 물으면 느리고 비싸고 실행마다 달라진다.

**Independent Test**: 같은 데이터소스·스키마로 두 번 계획을 뽑아 결과가 **바이트 단위로 동일**
한지 확인한다.

**Acceptance Scenarios**:

1. **Given** 카탈로그에 테이블 구조와 외래키가 있고 **When** 데이터소스와 스키마를 지정해
   생성하면 **Then** LLM 호출 없이 클래스·속성·관계가 만들어진다
2. **Given** 같은 데이터소스·스키마이고 **When** 계획을 두 번 뽑으면 **Then** 두 결과가 완전히
   동일하다
3. **Given** 생성이 끝났고 **When** 만들어진 클래스를 보면 **Then** 전부 데이터소스에 바인딩된
   가상 클래스이며 저장된 인스턴스는 0 이다
4. **Given** 생성이 끝났고 **When** 인제스천을 한 번도 하지 않은 상태에서 조회하면 **Then**
   실제 행이 돌아온다

---

### User Story 2 - 쓰기 전에 무엇이 만들어질지 본다 (Priority: P1)

수십 개 클래스가 한 번에 생기는 작업이다. 사용자는 먼저 계획(클래스·관계·속성 수와 목록)을
보고 나서 생성한다.

**Why this priority**: 되돌리기가 비싸다. 미리보기가 없으면 사용자는 결과를 보고서야 잘못된
스키마를 골랐다는 것을 안다.

**Independent Test**: 미리보기를 요청한 뒤 아무것도 만들어지지 않았음을 확인하고, 그 다음
생성해서 미리보기가 이름 지은 것들이 실제로 존재하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 데이터소스와 스키마를 골랐고 **When** 미리보기를 요청하면 **Then** 클래스·관계·
   속성 수와 목록이 표시되고 **아무것도 저장되지 않는다**
2. **Given** 미리보기를 아직 하지 않았고 **When** 생성 버튼을 보면 **Then** 비활성이다
3. **Given** 미리보기 결과가 클래스 이름들을 나열했고 **When** 생성하면 **Then** 나열된 클래스가
   전부 존재하고 전부 가상 클래스다
   ↳ E2E `catalog_shortcut.spec.js` [6]

---

### User Story 3 - 지름길은 답할 수 있을 때만 제안한다 (Priority: P2)

데이터소스만 고른 상태에서는 어느 테이블을 읽어야 할지 알 수 없다. 스키마까지 고른 뒤에만
지름길이 나타난다.

**Why this priority**: 잘못된 시점의 제안은 잘못된 결과를 만든다. 다만 없어도 정식 경로로
같은 일을 할 수 있다.

**Independent Test**: 데이터소스만 선택한 상태와 스키마까지 선택한 상태에서 지름길의 노출
여부를 비교한다.

**Acceptance Scenarios**:

1. **Given** 데이터소스만 선택했고 **When** 소스 단계를 보면 **Then** 지름길이 없다
2. **Given** 스키마까지 선택했고 **When** 소스 단계를 보면 **Then** 지름길이 나타나고 LLM 이
   필요 없다는 것이 표시된다
   ↳ E2E `catalog_shortcut.spec.js` [1][2]

---

### User Story 4 - 에이전트도 이 경로를 고를 수 있다 (Priority: P3)

정식 빌드 중에 골든퀘스천이 테이블로 답해지는 것이라면, 에이전트가 클래스를 하나씩 설계하는
대신 이 결정적 경로를 선택한다.

**Why this priority**: 편의다. 사용자가 UI 에서 직접 고르는 것으로 이미 목적은 달성된다.

**Independent Test**: 테이블로 답해지는 골든퀘스천으로 빌드를 돌려 에이전트가 이 경로를
쓰는지 본다.

**Acceptance Scenarios**:

1. **Given** 골든퀘스천이 카탈로그 테이블로 답해지고 **When** 빌드가 진행되면 **Then**
   에이전트가 클래스를 개별 설계하는 대신 카탈로그 생성 경로를 호출할 수 있다

---

### Edge Cases

- **컬럼명이 전부 대문자다** (Oracle 등) → 단어 경계가 살아야 한다. `MFG_PRODUCT` 는
  `MfgProduct` 이고 `MFGPRODUCT` 가 아니다. 반대로 의도적인 camelCase(`orderID`)는 보존한다.
  ↳ 단위 테스트가 실제로 이 버그를 잡았다
- **외래키 형태가 카탈로그마다 다르다** → `REFERENCES` / `FK_TO` / `FK_TO_TABLE` 을 모두 시도해
  중복을 제거해야 한다. 어느 서비스가 먼저 부팅했는지에 따라 존재하는 형태가 달라진다.
  ↳ constitution 원칙 III · 실측: `REFERENCES` 12건, 나머지 0건
- **다른 DB 에 같은 `schema.table` 이 있다** → 카탈로그의 테이블 MERGE 키가 DB 를 포함하지
  않아 노드가 합쳐질 수 있다. 조회 시 **항상** 데이터소스로 함께 필터링해야 한다.
  ↳ constitution 원칙 II
- **컬럼 타입이 한쪽 표기에만 있다** → 두 표기를 모두 받아야 한다. 한쪽만 읽으면 값이 있는데도
  전부 `unknown` 이 된다. ↳ constitution 원칙 III
- **이미 같은 이름의 클래스가 있다** → 생성은 멱등이어야 한다. 두 번 돌려도 같은 상태다.
  그래서 E2E 는 전후 차이(diff)가 아니라 **계획이 이름 지은 것의 존재**를 확인한다.
- **선택한 스키마에 테이블이 없다** → 무엇이 없는지 알려야 한다. 빈 온톨로지를 조용히 만들지
  않는다.

## Requirements *(mandatory)*

### Functional Requirements — 매핑 규칙

- **FR-001**: 시스템은 카탈로그를 다음 규칙으로 온톨로지에 매핑해야 한다. 규칙은 고정이며
  실행마다 달라지지 않는다.
  | 카탈로그 | 온톨로지 |
  |---|---|
  | 테이블 | 클래스 (PascalCase, `mfg_daily_equipment` → `MfgDailyEquipment`) |
  | 컬럼 | 속성 (SQL 타입 → 온톨로지 타입) |
  | 기본키 | 키 컬럼 |
  | 외래키 | 관계 유형 (UPPER_SNAKE, `REFERENCES_<TARGET_TABLE>`) |
  ↳ constitution ontology-studio 절 · `schema_ontology.py`
- **FR-002**: 클래스명은 영문 PascalCase, 관계 유형명은 영문 UPPER_SNAKE_CASE 여야 한다 —
  빌드 에이전트가 쓰는 규약과 같아야 한다. 생성된 온톨로지가 손으로 만든 것과 이질적으로 보이면
  안 된다.
- **FR-003**: 전부 대문자인 이름 조각은 title-case 로 바꿔 단어 경계를 유지하고, 혼합
  대소문자는 그대로 보존해야 한다.
  ↳ `test_schema_ontology.py` — `MFG_PRODUCT` → `MfgProduct`
- **FR-004**: **모든** 컬럼이 속성이 돼야 한다. 참조 구현(domain-layer)은 기본키와 `*_id` 를
  제외했지만, 여기서는 컬럼 매핑이 곧 조회 허용 목록이므로 제외하면 질의로 도달할 수 없다.
  참조 컬럼은 숨기는 대신 참조임을 표시한다.
- **FR-005**: 생성된 클래스는 기본적으로 **가상 클래스로 바인딩**돼야 한다. 인스턴스를
  복제하지 않는다.
- **FR-006**: 생성은 멱등이어야 한다. 같은 카탈로그로 두 번 실행해도 같은 상태가 된다.

### Functional Requirements — 카탈로그 읽기

- **FR-007**: 구조는 **인제스천 이후 Neo4j 카탈로그**에서 읽어야 한다. 소스 DB 를 다시
  introspect 하지 않는다. ↳ constitution 원칙 I
- **FR-008**: 테이블 조회는 **항상** 데이터소스로 함께 필터링해야 한다. 카탈로그의 테이블
  정체성이 DB 를 포함하지 않아 서로 다른 DB 의 동명 테이블이 합쳐질 수 있다.
  ↳ constitution 원칙 II
- **FR-009**: 컬럼 타입·기본키 여부는 **두 표기를 모두** 받아야 한다.
  ↳ constitution 원칙 III
- **FR-010**: 외래키는 세 가지 형태를 모두 시도해 중복을 제거해야 한다.
  ↳ constitution 원칙 III
- **FR-011**: 컬럼 순서는 카탈로그의 순서 정보를 따르고, 없으면 이름순으로 안정 정렬해야 한다.
  정렬이 불안정하면 FR-006 의 멱등성과 결정성 검증이 깨진다.

### Functional Requirements — 결정성과 안전성

- **FR-012**: 이 경로는 **LLM 을 호출하지 않아야** 한다. 프롬프트로 부탁하는 것이 아니라 경로
  자체에 모델 호출이 없어야 한다. ↳ constitution ontology-studio 절
- **FR-013**: 쓰기 전에 계획만 반환하는 모드가 있어야 하고, 그 모드는 아무것도 저장하지 않아야
  한다.
- **FR-014**: 계획에는 만들어질 클래스·관계·속성의 수와 목록이 담겨야 한다. 사용자가 수십 개를
  보지 않고 만들게 하지 않는다.
- **FR-015**: 대상 스키마에 테이블이 없으면 그 사실을 알려야 한다. 빈 온톨로지를 조용히 만들지
  않는다.

### Functional Requirements — 진입점

- **FR-016**: 사용자는 구축 브리프의 소스 단계에서 이 경로를 선택할 수 있어야 한다.
- **FR-017**: 그 지름길은 데이터소스와 **스키마가 모두** 선택된 뒤에만 나타나야 한다. 스키마
  없이는 어느 테이블을 읽어야 할지 알 수 없다.
- **FR-018**: 미리보기 전에는 생성을 실행할 수 없어야 한다.
- **FR-019**: 지름길에는 LLM 이 필요 없다는 사실이 표시돼야 한다. 이것이 사용자가 이 경로를
  고르는 이유다.
- **FR-020**: 빌드 에이전트도 이 경로를 도구로 호출할 수 있어야 하고, 골든퀘스천이 테이블로
  답해질 때 개별 설계 대신 이 경로를 고르도록 안내받아야 한다.

### Key Entities

- **생성 계획**: 만들어질 클래스(이름·원 테이블·속성 수), 관계(유형·출발·도착·근거 외래키),
  집계 수치. 저장 전 상태.
- **클래스 매핑**: 테이블 하나 ↔ 클래스 하나. 원 테이블 이름을 보존해 다시 확인할 수 있어야
  한다.
- **속성 매핑**: 컬럼 하나 ↔ 속성 하나. 원 컬럼명, 온톨로지 타입, 기본키 여부, 참조 여부.

## Assumptions

- 인제스천이 **이미 끝났다.** 등록만 되고 메타데이터가 추출되지 않은 데이터소스는 대상이
  아니다. 이 기능은 추출을 대신 하지 않는다.
- 외래키가 카탈로그에 있어야 관계가 생긴다. 소스 DB 에 FK 제약이 없으면 클래스만 생기고 관계는
  비어 있다 — 이 경우 관계는 사람이나 에이전트가 보완할 몫이다.
- 카탈로그의 writer 는 data-fabric 하나다. 이 기능은 읽기만 한다.
- 생성 결과는 [001](../001-datasource-backed-virtual-classes/spec.md) 의 가상 클래스이므로,
  조회·행위·SQL 안전성·기밀 유지 요구사항은 그 스펙을 따른다. 여기서 다시 정의하지 않는다.
- 이식 원본은 `domain-layer/app/services/schema_extractor.py` 다. 매핑 규칙은 그것을 따르되,
  속성 제외 규칙(FR-004)과 SQL 파라미터 처리는 **의도적으로 다르게** 했다.
