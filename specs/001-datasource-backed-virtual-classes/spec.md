# Feature Specification: 데이터소스 기반 가상 클래스

**Feature Branch**: `001-datasource-backed-virtual-classes`

**Created**: 2026-07-30

**Status**: Implemented (backfilled) — 구현 후 역공학으로 작성

**Input**: "등록된 data source 내의 테이블과 조회조건을 기반한 온톨로지를 생성하고, 그걸
기반으로 데이터소스에 접근할 수 있는 온톨로지를 생성한다. 데이터소스가 존재하는 온톨로지는
단일 속성을 가지는 것이 아니라 행위로서 자신의 데이터를 가져올 수 있다. (…) 이건 질의시에
그 행위가 확장되는 것이다."

> **역공학 스펙이다.** 설계 문서에서 구현으로 내려간 것이 아니라 **동작하는 구현에서 거꾸로**
> 뽑았다. 각 요구사항은 실제 코드·테스트·실측에 대응하며 근거는 `↳` 줄에 있다. 검증되지 않은
> 항목은 "미검증"으로 명시했다.

## 왜 이 스펙이 플랫폼 단위인가

한 서비스 안에서 끝나지 않는다. 카탈로그는 **data-fabric** 이 쓰고, SQL 실행은
**neo4j-text2sql** 이 하고, 온톨로지는 **ontology-studio** 가 갖는다. 세 저장소 중 하나를
되돌리면 계약이 깨진다. 그래서 서브모듈의 `openspec/` 이 아니라 여기에 있다.

관련: [`.specify/memory/constitution.md`](../../.specify/memory/constitution.md) 원칙 I·V·VI ·
ontology-studio 절 · [`docs/catalog-schema.md`](../../docs/catalog-schema.md)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 문서 없이 데이터소스만으로 온톨로지를 구축한다 (Priority: P1)

이미 운영 DB에 진실이 있는 도메인(설비 가동 이력, 주문, 센서 측정치)에서는 문서를 만들어
파싱할 이유가 없다. 사용자는 등록된 데이터소스와 스키마를 고르고 의도·골든퀘스천만 주면,
에이전트가 카탈로그를 탐색해 클래스를 테이블에 바인딩한 온톨로지를 만든다.

**Why this priority**: 이 기능의 존재 이유다. 기존 경로(문서 → 파서 → 인스턴스 적재)는
운영 데이터를 **복제**해야 했고, 복제한 순간 낡는다.

**Independent Test**: 파일을 하나도 첨부하지 않고 데이터소스만 선택해 구축을 시작할 수 있고,
결과 온톨로지로 실제 행을 조회할 수 있다.

**Acceptance Scenarios**:

1. **Given** 메타데이터가 추출된 데이터소스가 등록돼 있고 **When** 파일 없이 데이터소스 +
   의도 + 골든퀘스천 1개로 구축을 시작하면 **Then** 시작이 활성화되고 빌드가 진행된다
2. **Given** 데이터소스도 파일도 선택하지 않았고 **When** 의도와 골든퀘스천만 채우면
   **Then** 시작할 수 없고 그 이유가 표시된다
3. **Given** 카탈로그 서비스가 내려가 있고 **When** 구축 브리프를 열면 **Then** 데이터소스
   선택 영역이 숨고 **문서 기반 구축 흐름은 그대로** 동작한다

---

### User Story 2 - 클래스가 행위로서 자기 데이터를 가져온다 (Priority: P1)

가상 클래스는 속성에 값이 채워진 인스턴스를 갖지 않는다. 대신 이름 붙은 파라미터화된
행위(behavior)를 갖고, 질의 시점에 그 행위가 실제 SQL로 확장된다.

**Why this priority**: 사용자 요구의 핵심 문장("행위로서 자신의 데이터를 가져올 수 있다")이
그대로 여기다. 스토리 1만 있고 이게 없으면 테이블 목록을 그린 그림에 그친다.

**Independent Test**: 행위를 하나 정의하고 인자를 주어 호출하면 운영 DB의 실제 행이
돌아오며, 같은 시점에 저장된 인스턴스 수는 0이다.

**Acceptance Scenarios**:

1. **Given** 클래스가 `(datasource, schema, table)` 에 바인딩됐고 **When** 파라미터화된 SQL
   템플릿으로 행위를 만들면 **Then** 저장 전에 스모크 실행이 돌고, 실패하면 **저장되지 않고**
   실패한 SQL과 원인이 보고된다
2. **Given** 저장된 행위가 있고 **When** 인자를 주어 호출하면 **Then** 실행된 SQL, 컬럼,
   실제 행, 행 수, 소요 시간, 출처(`datasource.schema.table`)가 함께 돌아온다
3. **Given** 가상 클래스에 행위와 조회 결과가 있고 **When** 그 클래스의 저장된 인스턴스를
   세면 **Then** **0** 이다
4. **Given** 답변 모드에서 데이터성 질문이 들어왔고 **When** 저장된 행위가 그 질문을 커버하면
   **Then** 자연어 폴백이 아니라 그 행위가 호출된다

---

### User Story 3 - 조회조건이 온톨로지의 일부가 된다 (Priority: P2)

"불량 판정된 것만", "최근 30일" 같은 조건은 질문마다 다시 쓰는 것이 아니라 바인딩에 한 번
선언되어 그 클래스의 **모든** 조회에 항상 적용된다.

**Why this priority**: 사용자 요구의 "조회조건을 기반한 온톨로지". 조건이 온톨로지 밖에 있으면
같은 클래스가 질문에 따라 다른 모집단을 뜻하게 된다.

**Independent Test**: base condition 을 선언한 뒤 아무 행위나 호출해서, 컴파일된 조건이 최종
SQL 에 들어있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 바인딩에 base condition 이 선언됐고 **When** 행위를 호출하면 **Then** 컴파일된
   조건이 최종 SQL 에 포함된다
2. **Given** base condition 이 선언됐고 **When** SQL 템플릿에 조건 삽입 마커가 없으면
   **Then** 행위 생성이 거부된다 — 조건이 조용히 무시되지 않는다

---

### User Story 4 - 대본에 없는 질문도 답한다 (Priority: P3)

저장된 행위가 커버하지 못하는 질문은 자연어 → SQL 폴백으로 처리한다. 단 최후 수단이며,
사용했다는 사실을 답변에 밝힌다.

**Why this priority**: 커버리지를 넓히지만 결정적이지 않다. P1·P2 없이는 의미가 없고, 끄고도
기능은 성립한다.

**Independent Test**: 어떤 행위도 커버하지 않는 질문을 던져 폴백이 발동하고 답변이 그 사실을
고지하는지 본다.

**Acceptance Scenarios**:

1. **Given** 저장된 행위가 질문을 커버하지 못하고 폴백이 켜져 있으면 **When** 질문하면
   **Then** 자연어 경로가 SQL 을 만들어 답하고, 답변에 폴백 사용을 밝힌다
2. **Given** 폴백이 만든 SQL 이 바인딩에 선언되지 않은 테이블을 건드리면 **When** 결과를
   받으면 **Then** 범위 밖(`out_of_scope`)으로 표시된다
3. **Given** 폴백이 비활성화됐으면 **When** 커버되지 않는 질문이 오면 **Then** 폴백을
   시도하지 않고 답할 수 없음을 밝힌다

---

### Edge Cases

- **소스 스키마가 바뀌어 컬럼이 사라졌다** → 행위 호출이 원 SQL 에러를 그대로 노출해야 한다.
  에이전트가 환각으로 메우지 않고 "데이터소스 스키마가 변경되어 조회에 실패했다"고 보고한다.
  바인딩 검증이 `missing_columns` / `new_columns` / `type_changes` 를 돌려준다.
- **카탈로그가 데이터소스를 알지만 컬럼을 모른다** (등록만 되고 메타데이터 미추출) → 바인딩을
  만들 수 없다. E2E 픽스처는 이런 데이터소스를 **건너뛰어야** 한다. 무조건 첫 번째를 고르면
  모든 스펙이 조용히 skip 되어 초록불로 보이지만 아무것도 검증하지 못한다. (실제로 겪었다)
- **행 수가 상한을 넘는다** → 잘렸다는 사실이 결과에 실려야 하고, 답변이 "상위 N건만"임을
  밝혀야 한다. 조용히 자르면 집계 답이 틀린다.
- **가상 클래스는 벡터 검색·그래프 통계에 보이지 않는다** — 인스턴스 노드도 임베딩도 없어서.
  발견 경로가 하나뿐이므로 그래프 통계가 가상 클래스를 **별도로** 보고해야 하고, 답변
  에이전트는 데이터성 질문에서 먼저 행위 목록을 조회해야 한다.
- **클래스를 삭제하거나 이름을 바꿨다** → 바인딩과 행위가 함께 삭제/개명돼야 한다. 남으면
  존재하지 않는 클래스에 붙은 SQL 이 떠돈다.
- **materialized 클래스에 인스턴스 조회를 걸었다** → 그래프 검색으로 투명하게 위임한다.
  답변 에이전트가 클래스 종류로 분기하지 않아도 되게.

## Requirements *(mandatory)*

### Functional Requirements — 카탈로그 탐색

- **FR-001**: 시스템은 등록된 데이터소스 목록, 스키마, 테이블, 컬럼, 샘플 행을 조회할 수
  있어야 한다. 구조 정보는 **인제스천 이후 Neo4j 카탈로그**에서 읽고, 소스 DB 의
  `information_schema` 를 다시 뒤지지 않는다.
  ↳ constitution 원칙 I · `ontology-studio/backend/src/modules/ontology/datafabric_client.py`
- **FR-002**: 카탈로그 응답의 속성명 불일치(`type`↔`dtype`, `primary_key`↔`is_primary_key`,
  `datasource`↔`db`)는 **한 곳에서만** 흡수해야 한다. 호출부마다 재발명하면 다음 divergence
  에서 다시 하루가 든다.
  ↳ constitution 원칙 III · `_normalize_column()` · `test_datafabric_client.py`
- **FR-003**: 카탈로그가 응답하지 않을 때 예외를 전파하지 않고 저하 상태를 표시해야 한다.
  문서 기반 구축 경로는 영향을 받지 않는다.
- **FR-004**: 카탈로그 조회 결과는 캐시할 수 있으나, 새로 등록된 데이터소스를 즉시 볼 수 있는
  **강제 갱신** 수단이 있어야 한다.
  ↳ TTL 캐시가 새 데이터소스를 5분간 숨기는 문제를 실제로 겪었다

### Functional Requirements — 클래스 바인딩

- **FR-005**: 클래스는 `(datasource, source_schema, table)` 에 바인딩될 수 있고, 바인딩된
  클래스는 `virtual`, 아닌 클래스는 `materialized` 로 구분돼야 한다. 기존 클래스는 기본값으로
  `materialized` 가 되어 동작이 변하지 않아야 한다.
- **FR-006**: 바인딩은 컬럼→속성 매핑을 갖고, **그 매핑이 곧 조회 허용 목록**이어야 한다.
  매핑되지 않은 컬럼은 인스턴스 조회로 도달할 수 없다.
- **FR-007**: 바인딩 생성 시 컬럼명을 실제 카탈로그와 대조하고, 모르는 컬럼이 있으면
  **아무것도 저장하지 않고** 어느 컬럼이 문제인지 알려야 한다.
- **FR-008**: 바인딩 저장 시 클래스의 속성 목록을 매핑에서 파생해 동기화해야 한다. 스키마
  패널과 그래프가 여전히 실제 속성을 봐야 한다.
- **FR-009**: 클래스 삭제·개명 시 바인딩과 행위가 함께 삭제·개명돼야 한다.
  ↳ `test_binding_store.py`

### Functional Requirements — 행위(Behavior)

- **FR-010**: 가상 클래스는 이름·설명·파라미터 명세·SQL 템플릿·결과 형태를 가진 행위를 여러 개
  가질 수 있어야 한다. 바인딩이 없는 클래스에는 행위를 만들 수 없다.
- **FR-011**: 행위는 **저장 전에 스모크 실행**을 통과해야 한다. 실패하면 저장하지 않고 실행한
  SQL 과 원인을 돌려준다. 필수 파라미터에 기본값이 없어 실행할 수 없으면 그 사실을 명시한다.
- **FR-012**: 행위 호출은 실행된 SQL, 컬럼, 행, **실제** 행 수, 소요 시간, 출처를 돌려줘야
  한다. 에이전트에 주는 행은 직렬화 **전에** 잘라야 한다 — 사후 문자열 절단은 행 중간을 잘라
  유효하지 않은 JSON 을 만든다.
- **FR-013**: 온톨로지 속성명으로 인스턴스를 조회하는 **통일된 동사**를 제공해야 한다. 대상이
  materialized 클래스면 그래프 검색으로 투명하게 위임한다.
- **FR-014**: 민감(PII)으로 표시된 컬럼은 조회 결과에서 제외돼야 한다.

### Functional Requirements — SQL 안전성 (비타협)

- **FR-015**: SQL 파라미터는 **이스케이프하지 않고 타입으로 렌더**해야 한다. 정수·실수는 강제
  변환해 주입이 구조적으로 불가능하게 만든다.
  ↳ constitution ontology-studio 절 · `bind_sql_template()` · `test_sql_binder.py`
- **FR-016**: 문자열 파라미터에 따옴표·세미콜론·주석 기호·백슬래시·제어문자가 있으면 **거부**
  해야 한다. 이스케이프해서 통과시키지 않는다. 따옴표가 정당하게 필요하면 별도의 명시적 타입을
  선택해야 하고, 그 타입만이 유일하게 quote doubling 을 한다.
  ↳ 참조 구현(domain-layer)의 `value.replace("'", "''")` + 문자열 연결 패턴은 **복사하지 않는다**
- **FR-017**: 행 수 상한은 **호출자가 정할 수 없다.** 요청값·행위별 상한·전역 상한의 최솟값을
  적용한다. 템플릿에 `LIMIT` 이 들어있으면 행위 생성을 거부한다.
- **FR-018**: SQL 은 바인딩에 선언된 테이블만 참조할 수 있고, **생성 시점과 호출 시점 모두**
  검사해야 한다. 한쪽만 검사하면 나중에 바인딩이 좁아졌을 때 구멍이 남는다.
- **FR-019**: 실행 계층은 읽기 전용을 강제해야 한다. 클라이언트 사전검사는 에이전트에게 빠른
  피드백을 주기 위한 **자문**일 뿐이며, 서버 측 가드가 권위자다.

### Functional Requirements — 기밀 유지

- **FR-020**: 온톨로지 쪽은 DB 자격증명을 보유하지 않아야 한다. 데이터소스는 **이름으로만**
  지칭하고 접속 정보는 실행 서비스가 갖는다.
  ↳ constitution 원칙 V — 카탈로그의 `:DataSource` 노드는 비밀번호를 **평문**으로 갖고 있다
- **FR-021**: SQL 템플릿은 스키마 조회 응답과 외부(MCP) 표면에 **절대** 나타나지 않아야 한다.
  전용 상세 조회로만 얻을 수 있다.
- **FR-022**: 외부 표면에는 `{datasource, schema, table}` 수준만 노출한다. 호스트·포트·계정은
  노출하지 않는다.
- **FR-023**: 외부 클라이언트의 라이브 데이터 확장은 **기본 비활성**이어야 한다.
- **FR-024**: 로그에는 실행한 SQL 과 행 수만 남기고 접속 정보는 남기지 않는다.

### Functional Requirements — 질의 시점 라우팅

- **FR-025**: 답변 경로는 정해진 순서를 지켜야 한다 — 저장된 행위 → 속성 필터 조회 → (최후)
  자연어 폴백.
- **FR-026**: 자연어 폴백은 개별 스위치로 끌 수 있어야 한다. 폴백은 SQL 작성을 외부에
  위임하므로 **컬럼 허용 목록이 적용되지 않는다** — 스키마 범위 지정과 사후 테이블 검사만
  남는다. 이것이 별도 스위치를 두는 이유다.
- **FR-027**: 빌드 시 검증 도구 목록에 자연어 폴백을 **등록하지 않아야** 한다. 검증은
  결정적이어야 한다. 프롬프트로 말리는 대신 도구를 빼서 구조적으로 막는다.
- **FR-028**: 답변은 그래프 근거(노드)와 데이터 근거(`datasource.table`, 행 수)를 함께 밝혀야
  한다. 숫자는 조회 결과를 인용하고 직접 계산하지 않는다 — 집계는 SQL 이 한다.
- **FR-029**: 결과가 잘렸으면 답변이 그 사실을 밝혀야 한다.

### Key Entities

- **가상 클래스 바인딩**: 클래스 하나가 어느 데이터소스의 어느 테이블을 뜻하는지, 어떤 컬럼이
  어떤 속성인지, 어떤 조건이 항상 적용되는지, 키가 무엇인지. 조인 허용 테이블 목록을 포함한다.
- **행위(Behavior)**: 가상 클래스가 소유하는, 이름 붙은 파라미터화된 조회. 파라미터 명세(이름·
  타입·필수·기본값·허용값), SQL 템플릿, 결과 형태, 행 상한, 마지막 검증 시각·행 수를 갖는다.
- **base condition**: 그 클래스의 모든 조회에 항상 적용되는 조건. 컬럼·연산자·값·값 타입.
- **조회 결과**: 컬럼, 행, 실제 행 수, 실행된 SQL, 출처, 잘림 여부.

## Assumptions

- 데이터소스는 이 기능 **밖에서** 등록되고 메타데이터가 추출돼 있다. 등록만 되고 추출되지 않은
  데이터소스는 바인딩 대상이 아니다.
- 카탈로그의 writer 는 하나(data-fabric)다. 이 기능은 카탈로그를 **읽기만** 하므로 새
  divergence 를 만들지 않는다.
- 실행 서비스가 SQL 가드와 dialect 처리를 담당한다. 클라이언트 검증은 그 위에 얹는 이중
  방어이며 대체가 아니다.
- 행 상한 500 은 실행 엔진(MindsDB)이 그 이상에서 연결을 끊는 실측에서 나왔다. 페이징보다
  SQL 집계를 선호한다.
- 조회 경로는 게이트웨이(9000)를 경유하지 않는다. 기본 응답 타임아웃 30초가 10~25초짜리
  view 질의를 끊는다.
- 로컬 구성에서는 온톨로지와 카탈로그가 **같은** Neo4j 를 공유한다. 그래서 전역 삭제가
  카탈로그를 지운다 (constitution 원칙 IV).
