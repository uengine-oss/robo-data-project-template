# Feature Specification: 이식 가능한 에이전트 스킬 패키지

**Feature Branch**: `005-portable-agent-skills`

**Created**: 2026-08-02

**Status**: Draft

**Input**: User description: "ontology-studio 는 cliagent 를 통하여 스킬 기반으로 외부 에이전트를
통하여 실행할 수 있도록 되어있는데, 그 skill 만으로 사용할 사용자들을 위하여 일반적인 skill
파일로도 분리하고, 폴더로 구분되어있으면 좋겠다. 그리고 그게 deepagents 와 cliagents 들에 동시에
사용되도록. 그렇게 하여 claude code ui에서 직접 설치하여 사용할 수도 있게."

## 관계

[004](../004-pluggable-agent-backend/spec.md) 는 **누가 에이전트를 돌리는가**를 교체 가능하게
만들었다. 이 스펙은 그 위에서 **지시문 자체를 스튜디오 밖으로 꺼낸다.**

004 는 시스템 프롬프트를 마크다운 한 장으로 만들고(FR-020) cliagents 가 그것을 에이전트 관례에 맞는
위치로 내보내게 했다(FR-021). 다만 그 마크다운은 스튜디오 내부 파일이다 — 이름도 `ontology_build.md`
처럼 파이썬 모듈 옆에 붙어 있고, 프론트매터가 없어 어느 에이전트도 **스스로 발견하지 못한다.**
스튜디오 백엔드가 읽어서 넣어 줘야만 작동한다.

이 스펙은 그 파일을 **자립하는 스킬 패키지**로 승격한다. 스튜디오 화면을 열지 않아도 사용자가 자기
Claude Code 에 직접 설치할 수 있는 형태다.

루트에 두는 이유는 004 와 같다 — 되돌리면 계약이 깨진다:

- 스킬 패키지의 정식 위치와 이름 (두 백엔드와 외부 설치본이 모두 이 이름에 의존한다)
- 외부 설치본이 붙는 MCP 엔드포인트 `/mcp/agent-bridge/{mode}` — 004 가 만든 것을 **공개 계약**으로
  승격한다
- 스킬의 **입력 계약** — 스튜디오 폼과 단독 실행의 인터뷰가 같은 항목을 채운다. 지금 백엔드 코드에만
  있는 이 골격이 스킬로 올라온다

## 배경 — 왜 스킬을 꺼내야 하는가

지금 스킬 본문은 스튜디오 백엔드만 읽을 수 있다:

- 위치가 `backend/src/modules/agent_session/skills/*.md` — 파이썬 패키지 내부다
- 발견용 메타데이터가 없다. 외부 에이전트는 이름과 한 줄 설명이 있어야 스킬을 목록에 올린다
- 본문이 `/workspace/uploads` 를 말한다. 실제 호스트 경로는 cliagents 백엔드가 **런타임에 덧붙이는**
  주석으로만 알려 준다. 파일만 복사해 가면 존재하지 않는 경로를 가리킨다
- 어떤 도구가 필요한지(= 어느 MCP 서버에 붙어야 하는지) 본문 어디에도 없다
- 스킬 이름이 백엔드 코드에 하드코딩되어 있다. 스킬을 늘리려면 코드를 고쳐야 한다
- **작업 지시의 골격을 파이썬이 조립한다.** 구축 의도·연결 데이터소스·골든 퀘스천·이전 검토
  피드백·완료 기준은 스킬 본문이 아니라 백엔드 코드가 문자열로 붙인다. 스튜디오 폼이 채워 주는
  값이기 때문이다. 단독 실행자에게는 **이 골격이 통째로 없다** — 스킬만 읽은 에이전트는 자기가
  무엇을 받아야 하는지조차 모른다

그래서 "스튜디오 화면은 안 쓰고 이 온톨로지 구축 방법론만 내 Claude Code 에서 쓰고 싶다" 는
사용자에게 줄 것이 없다. 파일을 복사해 줘도 동작하지 않는다.

**중요한 전제 하나** — 표준 스킬 형식(폴더 + 프론트매터 + 점진적 공개)은 세 소비자가 **이미 모두
이해한다.** 외부 CLI 에이전트는 물론이고, 내장 경로가 쓰는 deepagents 에도 같은 규격의 스킬 적재
기능이 들어 있다(현재 배선되어 있지 않을 뿐이다). 즉 이 스펙은 새 규격을 발명하는 것이 아니라
**이미 있는 규격으로 옮겨 타는 것**이고, 그래서 "본문을 나누면 한쪽만 게을리 읽는다" 는 걱정이
성립하지 않는다.

동시에 반대 방향의 제약도 분명하다. 스킬을 밖으로 꺼내면서 **두 백엔드가 서로 다른 지시문을 읽게
되면** 004 FR-020 이 무너진다. 한쪽에서 고친 것이 다른 쪽에 반영되지 않는 상태가 정확히 이 스펙이
막아야 하는 실패다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스튜디오 화면 없이 스킬만으로 쓴다 (Priority: P1)

Claude Code 를 쓰는 사용자가 스튜디오 화면을 열지 않고, 자기 터미널의 Claude Code 에 온톨로지 구축
스킬을 설치해 그대로 온톨로지를 만든다.

**Why this priority**: 이 스펙의 존재 이유. 이것이 안 되면 폴더를 나누는 일은 정리정돈에 불과하다.

**Independent Test**: 스튜디오 프론트엔드를 띄우지 않은 상태에서, 스킬을 설치한 Claude Code 에
문서와 골든 퀘스천을 주고 구축을 시키면 그래프가 만들어지고 검증 리포트가 나온다.

**Acceptance Scenarios**:

1. **Given** 스킬을 설치한 Claude Code 세션, **When** 사용자가 "온톨로지 구축" 을 요청한다,
   **Then** 에이전트가 설치된 스킬을 **스스로 찾아** 로드한다 (사용자가 파일 경로를 알려 주지 않는다).
2. **Given** 스킬은 설치됐지만 도구 연결이 안 된 상태, **When** 스킬이 로드된다, **Then** 무엇이
   빠졌는지와 어떻게 연결하는지를 알려 주고 멈춘다. 도구 없이 그럴듯한 답을 지어내지 않는다.
3. **Given** 스킬 + 도구 연결이 모두 된 상태, **When** 질의 응답 스킬로 004 와 같은 질문을 묻는다,
   **Then** 스튜디오 경로와 **같은 답**이 나오고 근거로 데이터소스·테이블·행 수를 제시한다.
4. **Given** 스킬만 설치한 사용자, **When** 작업 디렉터리를 정한다, **Then** 스킬이 말하는 입력·출력
   경로가 그 사용자의 실제 디렉터리를 가리킨다 (`/workspace` 같은 존재하지 않는 경로가 아니다).

---

### User Story 2 - 부족한 입력을 스킬이 스스로 묻는다 (Priority: P1)

스튜디오 화면에서는 폼이 구축 의도·골든 퀘스천·데이터소스·전략을 채워 준다. 단독 실행에는 그 폼이
없다. 스킬이 **자기 입력을 스스로 확보**해야 한다 — 없는 것만 묻고, 이미 다 받았으면 해석한 바를
확인만 하고 넘어간다.

**Why this priority**: 이것이 없으면 단독 실행은 "무엇을 만들지 모르는 채로 시작" 한다. 골든 퀘스천이
모든 것을 결정하는 방법론에서 그건 구축이 아니라 추측이다. US1 을 실질적으로 성립시키는 조건이다.

**Independent Test**: 같은 스킬에 (a) 아무 정보 없이 "온톨로지 만들어줘" 만 주는 경우와 (b) 의도·골든
퀘스천·데이터소스를 모두 갖춘 요청을 주는 경우를 각각 넣으면, (a) 는 묻고 (b) 는 확인만 하고 진행한다.

**Acceptance Scenarios**:

1. **Given** 단독 실행에서 아무 맥락 없이 구축을 요청한다, **When** 스킬이 로드된다, **Then** 설계를
   시작하기 전에 부족한 입력(구축 의도, 골든 퀘스천, 대상 소스)을 **묻는다.** 임의로 지어내고
   진행하지 않는다.
2. **Given** 요청에 구축 의도·골든 퀘스천·데이터소스가 모두 들어 있다, **When** 스킬이 로드된다,
   **Then** **묻지 않는다.** 무엇으로 이해했는지 요약해 보이고 그대로 진행한다.
3. **Given** 일부만 들어 있다(예: 의도는 있고 골든 퀘스천이 없다), **When** 스킬이 로드된다,
   **Then** **빠진 것만** 묻는다. 이미 준 것을 다시 묻지 않는다.
4. **Given** 문서와 데이터소스가 모두 확보됐다, **When** 전략을 정한다, **Then** 어떤 전략이
   가능한지 근거와 함께 제시하고 사용자가 고르게 한다. 조용히 하나를 골라 진행하지 않는다.
5. **Given** 스튜디오 화면에서 폼을 모두 채워 구축을 시작한다, **When** 같은 스킬이 실행된다,
   **Then** 인터뷰가 발동하지 않는다 — 확인 요약 후 바로 설계에 들어간다.
6. **Given** 스튜디오 화면에서 구축 의도를 비워 두고 시작한다, **When** 같은 스킬이 실행된다,
   **Then** 단독 실행과 **같은 질문**을 한다. 화면이라고 다르게 굴지 않는다.
7. **Given** 스킬이 물었다, **When** 사용자가 답한다, **Then** 답한 내용이 이후 설계·검증의 기준으로
   쓰인다 (골든 퀘스천은 원문 그대로 유지된다).

### User Story 3 - 두 백엔드가 같은 스킬을 읽는다 (Priority: P1)

deepagents 경로와 cliagents 경로가 같은 스킬 패키지를 단일 소스로 읽는다. 스킬을 한 번 고치면 두
경로에 동시에 반영된다.

**Why this priority**: 004 FR-020 의 보존. 갈라지면 이 스펙은 문제를 하나 더 만든 것이 된다.

**Independent Test**: 스킬 본문에 식별 가능한 문장을 하나 넣고 두 백엔드를 각각 실행하면, 양쪽 모두
그 문장이 지시문에 들어간 것을 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 스킬 패키지의 한 문장을 수정한다, **When** deepagents 경로와 cliagents 경로를 각각
   실행한다, **Then** 두 경로 모두 수정된 문장을 지시문으로 갖는다.
2. **Given** `AGENT_BACKEND` 미설정(deepagents 기본), **When** 기존 백엔드 테스트 전체를 돌린다,
   **Then** 전부 통과한다.
3. **Given** `AGENT_BACKEND=cliagents`, **When** 004 의 구축·질의 시나리오를 돌린다, **Then** 004 에
   기록된 결과와 동등하게 완주한다.
4. **Given** 스킬 패키지가 발견용 메타데이터를 갖는다, **When** deepagents 가 이를 스킬로 적재한다,
   **Then** 메타데이터가 지시문 본문으로 새어 들어가지 않는다.
5. **Given** 세부 지침이 참조 자료로 분리되어 있다, **When** 두 백엔드가 각각 그 세부가 필요한
   작업(예: PDF 파서 작성)을 한다, **Then** 양쪽 모두 해당 참조 자료를 실제로 읽고 그 규칙을 따른다.

---

### User Story 4 - 스킬을 하나 더 추가한다 (Priority: P2)

구축·질의 말고 다른 목적의 스킬(예: 스키마 리뷰, 데이터소스 진단)을 폴더 하나 추가하는 것으로
늘린다.

**Why this priority**: 폴더로 나누는 일의 실질적 이득. 지금은 스킬 이름이 백엔드 코드에 하드코딩되어
있어 스킬을 늘리려면 코드를 고쳐야 한다.

**Independent Test**: 새 폴더에 스킬을 하나 만들고, 두 백엔드 어느 쪽에서도 코드 수정 없이 그것이
목록에 잡히는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 스킬 폴더를 하나 추가한다, **When** 스킬 목록을 조회한다, **Then** 코드 변경 없이 새
   스킬이 나타난다.
2. **Given** 메타데이터가 없거나 필수 항목이 빠진 폴더, **When** 로드한다, **Then** 조용히 무시하지
   않고 어느 폴더의 무엇이 잘못됐는지 지목한다.

---

### User Story 5 - 설치본을 최신으로 갱신한다 (Priority: P3)

이미 설치한 사용자가 새 버전의 스킬로 갱신하고, 자기가 어느 버전을 쓰고 있는지 안다.

**Why this priority**: 없어도 첫 배포는 성립한다. 다만 없으면 "왜 나는 그 동작이 안 되나" 를 진단할
수 없다.

**Independent Test**: 설치본에서 버전을 확인하고, 갱신 후 다시 확인하면 값이 달라진다.

**Acceptance Scenarios**:

1. **Given** 설치된 스킬, **When** 버전을 확인한다, **Then** 스킬 패키지가 자기 버전을 밝힌다.
2. **Given** 스킬 패키지가 갱신됐다, **When** 사용자가 재설치한다, **Then** 이전 설치본을 덮어쓰고
   남은 파일이 없다.

---

### Edge Cases

- **MCP 도구 없이 스킬만 로드됨**: 가장 흔한 실패 경로다. 도구가 없다는 것을 스킬이 **스스로 감지해
  보고**해야 한다. 조용히 추측으로 답하면 사용자는 온톨로지가 만들어졌다고 오해한다.
- **스튜디오 백엔드가 안 떠 있음**: 도구는 스튜디오 백엔드가 제공하므로 백엔드가 없으면 스킬
  단독으로는 그래프를 만들 수 없다. 이 전제를 스킬 본문이 명시해야 한다.
- **두 스킬이 동시에 로드됨**: 질의(읽기 전용) 스킬과 구축(쓰기) 스킬이 같은 세션에 함께 올라오면
  질의 모드의 읽기 전용 보장이 깨진다. 각 스킬이 자기 권한 경계를 본문에 명시해야 한다.
- **경로 표기가 환경마다 다름**: 스튜디오 샌드박스(`/workspace`), cliagents 호스트 경로, 외부 설치본의
  임의 작업 디렉터리 — 세 경우가 하나의 본문에서 성립해야 한다.
- **스킬 이름 충돌**: 사용자의 Claude Code 에 같은 이름의 스킬이 이미 있으면 덮어쓰기 전에 드러나야
  한다.
- **참조 자료를 읽지 않고 진행**: 본문만 읽고 파서를 쓰면 `content` 수집 규칙 같은 세부가 빠진 채
  그럴듯한 결과가 나온다. 실패가 조용해서 가장 위험하다.
- **참조 자료가 설치본에 안 딸려 옴**: 배포 단위가 본문 한 장만 담으면 세부가 통째로 사라진다.
  설치본은 폴더 전체여야 한다.
- **플러그인 설치와 폴더 복사가 겹침**: 같은 스킬이 두 경로로 각각 설치되면 어느 쪽이 이기는지가
  드러나야 한다.
- **인터뷰가 헤드리스에서 매달림**: 스튜디오 경로의 외부 CLI 는 헤드리스로 돈다. 004 실측에서
  구조화된 질문 도구는 그 환경에서 **제공되지 않았고**, 실질적 되묻기는 산문이었다. 질문은 턴을
  **끝내며** 남겨야 하고, 답을 기다리며 프로세스가 매달리면 안 된다.
- **되묻기가 끝나지 않음**: 사용자가 "알아서 해" 라고 답하는 경우가 있다. 무한히 캐묻지 말고, 정해진
  횟수 안에 확보한 것으로 진행하되 **무엇을 가정했는지 밝혀야** 한다.
- **입력이 다 있는데도 물음**: 확인을 질문으로 만들면 스튜디오 경로가 매 실행마다 한 턴씩 늘어난다.
  다 갖춰졌을 때는 요약만 하고 진행해야 한다.
- **사용자가 준 골든 퀘스천이 변형됨**: 검증 리포트가 원문과 다른 문장을 쓰면 사용자는 자기 질문이
  검증됐는지 알 수 없다.

## Requirements *(mandatory)*

### Functional Requirements — 스킬 패키지 형식

- **FR-001**: 각 스킬은 **자기 폴더 하나**를 가져야 한다. 폴더 이름이 곧 스킬 이름이고, 메타데이터의
  이름과 일치해야 한다.
- **FR-002**: 각 스킬 폴더는 에이전트가 스킬을 **발견**하는 데 필요한 메타데이터(이름, 한 줄 설명)를
  본문과 함께 갖춰야 한다. 사용자가 경로를 지정해 주지 않아도 에이전트가 목록에 올릴 수 있어야 한다.
- **FR-002a**: 형식은 세 소비자(deepagents, 외부 CLI 에이전트들, 사용자의 수동 설치)가 **공통으로
  이해하는 표준**이어야 한다. 우리만 아는 규격을 새로 만들지 않는다.
- **FR-003**: 스킬 본문은 **스튜디오 코드 없이 읽어서 실행 가능**해야 한다. 런타임에 백엔드가
  덧붙여야만 뜻이 통하는 문장이 남아 있으면 안 된다.
- **FR-004**: 스킬 본문은 자기가 필요로 하는 **도구와 그 출처**를 명시해야 한다.
- **FR-005**: 스킬 본문은 입력·출력 경로를 **환경에 무관하게** 기술해야 한다. 특정 환경의 절대 경로를
  본문에 못박지 않는다.
- **FR-006**: 각 스킬은 자기 **권한 경계**(읽기 전용인지 쓰기 가능한지)를 본문에 명시해야 한다.
- **FR-007**: 스킬 패키지는 자기 **버전**을 밝혀야 한다.

### Functional Requirements — 단일 소스

- **FR-010**: 스킬 본문은 저장소에 **한 벌만** 존재해야 한다. 두 백엔드가 같은 원본을 읽는다.
- **FR-011**: deepagents 경로는 **같은 스킬 폴더를 스킬로 적재**해야 한다. 폴더 내용을 시스템
  프롬프트로 통째 이식하는 지금 방식을 유지하지 않는다. 발견용 메타데이터가 지시문 본문으로 새어
  들어가면 안 된다.
- **FR-012**: cliagents 경로는 스킬 패키지를 각 에이전트 관례에 맞는 위치로 내보내야 한다(004
  FR-021 유지). 내보낼 때 내용을 다시 쓰지 않는다.
- **FR-013**: 스킬 목록은 폴더 스캔으로 결정되어야 한다. 스킬 이름이 코드에 하드코딩되면 안 된다.
- **FR-014**: 형식이 잘못된 스킬 폴더는 **거부하고 지목**해야 한다. 조용히 건너뛰면 안 된다.
- **FR-015**: 작업 지시의 골격(무엇을 받아 어떤 기준으로 끝내는가)은 **스킬에 있어야** 한다. 백엔드가
  같은 내용을 문자열로 다시 조립하면 FR-010 이 깨진다. 백엔드가 넘기는 것은 **값**이지 지시문이
  아니다.

### Functional Requirements — 배포와 설치

- **FR-020**: 스킬 패키지는 스튜디오를 설치하지 않고도 **가져갈 수 있는 형태**로 배포되어야 한다.
- **FR-021**: 설치 절차가 문서화되어야 하고, 그 문서만 보고 완주할 수 있어야 한다.
- **FR-022**: 설치본이 스튜디오 도구에 붙는 방법(MCP 연결)이 문서화되어야 한다. 스튜디오 백엔드가
  필요하다는 전제를 숨기지 않는다.
- **FR-023**: 재설치는 이전 설치본을 완전히 대체해야 한다. 옛 파일이 남으면 안 된다.
- **FR-024**: 배포는 **두 경로를 모두** 지원해야 한다.
  - **(a)** Claude Code UI 에서 바로 설치할 수 있는 플러그인 형태 — 사용자가 파일을 손으로 옮기지
    않는다.
  - **(b)** 폴더를 그대로 복사해도 동작하는 형태 — Claude Code 가 아닌 에이전트, 그리고 플러그인을
    쓰지 않으려는 사용자를 위해.
- **FR-025**: 두 경로가 **같은 스킬 폴더**를 배포해야 한다. 플러그인용으로 내용을 따로 가공하면
  FR-010 이 깨진다.

### Functional Requirements — 입력 확보와 초기 인터뷰

- **FR-050**: 스킬은 자기가 필요로 하는 **입력 항목을 본문에 명시**해야 한다 — 구축 의도, 골든
  퀘스천, 대상 소스(문서 / 데이터소스), 전략, 대상 스키마, 이전 검토 피드백. 지금 백엔드 코드가
  조립하는 골격이 곧 이 항목들이므로, 그 조립 규칙이 스킬로 넘어와야 한다.
- **FR-051**: 스킬은 작업 시작 전에 **주어진 입력을 점검**하고, **빠진 것만** 물어야 한다. 이미 받은
  것을 다시 묻지 않는다.
- **FR-052**: 모든 입력이 갖춰졌으면 **묻지 않고**, 무엇으로 이해했는지 **요약해 확인**한 뒤 진행해야
  한다. 확인이 사용자의 응답을 요구해서는 안 된다.
- **FR-053**: 호출 경로(스튜디오 / 단독 실행)에 따라 인터뷰 동작이 달라지면 안 된다. 차이는 **입력이
  채워져 있느냐**뿐이어야 한다.
- **FR-054**: 질문은 실행을 **매달아 두지 않는 방식**으로 이루어져야 한다. 헤드리스 환경에서 응답을
  기다리며 프로세스가 멈추면 안 된다.
- **FR-055**: 되묻기 횟수에 **상한**이 있어야 한다. 상한에 닿으면 확보한 것으로 진행하되 **가정한
  내용을 명시**해야 한다.
- **FR-056**: 문서와 데이터소스가 모두 있을 때처럼 **전략 선택지가 여럿인 경우**, 선택지와 근거를
  제시하고 사용자가 고르게 해야 한다(003 의 전략 추천을 인터뷰의 일부로 쓴다).
- **FR-057**: 사용자가 준 **골든 퀘스천 원문은 변형 없이 유지**되어야 한다. 검증 리포트도 같은 문장을
  쓴다.
- **FR-058**: 인터뷰로 확정된 입력은 이후 **설계·검증의 기준**으로 쓰여야 한다. 확인만 하고 버리면
  안 된다.

### Functional Requirements — 회귀 금지

- **FR-030**: `AGENT_BACKEND` 미설정 사용자에게 달라지는 것이 없어야 한다.
- **FR-031**: 004 에서 검증된 시나리오(질의 응답 동일 값, 문서 빌드 완주, 스티어링, 세션 재개)가 모두
  유지되어야 한다.
- **FR-032**: cliagents 백엔드 모듈은 langchain 계열을 import 하지 않는다는 004 FR-030 이 유지되어야
  한다. 스킬 로더가 이 경계를 넘으면 안 된다.

### Functional Requirements — 분량과 분할 (점진적 공개)

- **FR-040**: 스킬은 **개요 + 워크플로우**를 담은 본문과, 세부를 담은 **참조 자료**로 나뉘어야 한다.
  본문은 "언제 이 스킬을 쓰는가 / 어떤 순서로 진행하는가 / 어디를 더 읽어야 하는가" 를 담고, 분량이
  길어지는 세부(인제스천 패턴별 지침, 파서 작성 규칙, 도구별 사용법, 소스 타입별 파싱 가이드)는 참조
  자료로 내린다.
- **FR-041**: 본문은 각 참조 자료를 **언제 읽어야 하는지** 지목해야 한다. 참조 자료 목록만 나열하면
  에이전트는 읽지 않는다.
- **FR-042**: **두 백엔드 모두** 참조 자료를 실제로 읽을 수 있어야 한다. 한쪽만 세부를 못 읽으면
  같은 스킬을 쓰고도 결과가 갈린다 — 이 스펙이 막으려는 실패가 다른 형태로 재발한다.
- **FR-043**: 분할은 **내용을 옮기는 것**이지 다시 쓰는 것이 아니다. 분할 전후로 지시문의 총합이
  같아야 한다.
- **FR-044**: 참조 자료가 없거나 읽히지 않으면 본문만으로 진행하지 말고 **그 사실을 보고**해야 한다.
  세부 지침을 못 읽은 채 만든 파서는 조용히 품질이 무너진다.

### Key Entities

| 개념 | 설명 |
|---|---|
| 스킬 패키지 | 폴더 하나 = 스킬 하나. 발견용 메타데이터 + 본문 + 참조 자료 |
| 스킬 레지스트리 | 폴더를 스캔해 사용 가능한 스킬 목록을 만드는 것. 두 백엔드의 공통 진입점 |
| 본문 | 언제 쓰는가·어떤 순서로·어디를 더 읽는가. 에이전트가 항상 읽는 부분 |
| 참조 자료 | 필요할 때만 읽는 세부 지침. 본문이 언제 읽을지 지목한다 |
| 입력 계약 | 스킬이 일을 시작하기 위해 있어야 하는 항목들 (의도·골든 퀘스천·소스·전략·대상 스키마·검토 피드백). 지금은 백엔드 코드가 조립한다 |
| 초기 인터뷰 | 입력 계약의 빈칸을 메우는 절차. 다 차 있으면 확인만 하고 지나간다 |
| 도구 요구사항 | 그 스킬이 동작하려면 붙어 있어야 하는 도구 집합과 그 출처 |
| 권한 경계 | 그 스킬이 읽기 전용인지 쓰기 가능한지 |
| 배포본 | 스튜디오 없이 사용자가 설치하는 단위 |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 스튜디오 프론트엔드를 띄우지 않고 스킬만 설치한 상태에서 질의 응답이 스튜디오 경로와
  **같은 답**을 낸다.
- **SC-002**: 스튜디오 프론트엔드 없이 문서 구축이 클래스 생성 → 파서 작성 → 적재 → 검증까지
  완주한다.
- **SC-003**: 스킬 본문 문장이 저장소에 **한 곳에만** 존재한다 (중복 사본 0개).
- **SC-004**: `AGENT_BACKEND` 미설정 시 기존 백엔드 테스트가 **100%** 통과한다.
- **SC-005**: 004 에 기록된 cliagents 검증 항목이 **모두** 같은 결과로 재현된다.
- **SC-006**: 스킬을 하나 추가하는 데 필요한 **코드 변경이 0줄**이다 (폴더 추가만).
- **SC-007**: 설치 문서만 보고 처음 접한 사용자가 **10분 안에** 설치부터 첫 질의 응답까지 도달한다.
- **SC-008**: 도구가 연결되지 않은 상태에서 스킬을 쓰면 **100%** 명시적 안내로 멈춘다 (추측 답변
  0건).
- **SC-009**: 세부 지침이 필요한 작업에서 **두 백엔드 모두** 해당 참조 자료를 실제로 읽는다.
- **SC-010**: 분할 전후로 지시문의 총 내용이 동등하다 — 옮겨진 문장 외에 **사라진 지침이 없다.**
- **SC-011**: Claude Code UI 설치 경로와 폴더 복사 경로가 **같은 결과**를 낸다.
- **SC-012**: 맥락 없이 구축을 요청하면 **100%** 부족한 입력을 먼저 묻는다 (임의 진행 0건).
- **SC-013**: 입력이 모두 갖춰진 요청에서는 되묻기가 **0회**다 — 스튜디오 경로의 턴 수가 지금과 같다.
- **SC-014**: 같은 입력 상태에 대해 스튜디오 경로와 단독 실행이 **같은 질문**을 한다.
- **SC-015**: 사용자가 준 골든 퀘스천 문장이 검증 리포트에 **글자 그대로** 유지된다.

## Assumptions

- 스킬 단독 사용자도 **스튜디오 백엔드는 실행**한다. 도구(그래프 조작, 데이터소스 조회)는 004 가 만든
  MCP 브리지가 제공하며, 이 스펙은 도구를 재구현하지 않는다. 빠지는 것은 스튜디오 **프론트엔드**다.
- 대상 외부 에이전트는 004 가 이미 검증한 두 개(Claude Code, Codex)다. 새 에이전트 지원은 이 스펙의
  범위가 아니다.
- 스킬 본문의 언어는 현재대로 한국어를 유지한다.
- 스킬 폴더의 정식 위치는 저장소에서 배포 단위로 잘라낼 수 있는 곳으로 옮긴다. 파이썬 패키지
  내부(`backend/src/modules/agent_session/skills/`)는 배포 단위로 부적절하다.
- 기존 두 스킬(`ontology_build`, `ontology_answer`)의 **방법론 내용은 이 스펙에서 바꾸지 않는다.**
  본문/참조 자료로 재배치하고, 자립에 필요한 문장(도구 요구사항·경로 규약·권한 경계)만 더한다.
- deepagents 는 표준 스킬 폴더를 적재하는 기능을 이미 갖고 있다. 이 스펙은 그 기능을 **배선**하는
  것이지 새로 만드는 것이 아니다.
- deepagents 경로의 에이전트도 참조 자료를 읽을 파일 도구를 이미 갖고 있다(구축 모드는 파서를 쓰고
  실행하므로 필수다). 질의 응답 모드도 같은 전제가 성립하는지는 구현 시 확인 대상이다.
- 스튜디오 화면은 그대로 둔다. 폼은 계속 존재하고, 달라지는 것은 그 값이 **스킬의 입력 계약으로
  전달**된다는 점이다. 화면에서 폼을 없애거나 채팅으로 대체하지 않는다.
- 초기 인터뷰의 대상은 **구축 스킬**이다. 질의 응답 스킬은 질문 자체가 입력이므로 인터뷰가 필요
  없다. 다만 입력 계약을 본문에 밝히는 규칙(FR-050)은 두 스킬 모두에 적용된다.
- 되묻기 상한(FR-055)의 기본값은 구현 시 정한다. 상한이 존재한다는 것이 요구사항이고 구체적 숫자는
  아니다.
- 스킬 이름은 하이픈 표기(`ontology-build`)로 통일한다. 현재 cliagents 가 내보낼 때 이미 그렇게
  바꾸고 있다.

## Out of Scope

- 스킬 본문의 방법론 개선. 인제스천 패턴, 검증 절차, 프롬프트 품질은 그대로 옮긴다.
- 004 가 남긴 미해결 항목(AskUserQuestion 미발화, Codex 스티어링 불가, 내장 경로 컨텍스트 관리).
- 스킬 마켓플레이스 운영(심사, 통계, 사용자 계정).
- 스튜디오 화면에서 스킬을 편집하는 UI.
- 스튜디오 구축 폼의 개편. 폼은 그대로 두고 값의 전달 방식만 계약화한다.
- 구조화된 선택지 UI 로 인터뷰를 렌더링하는 것. 004 실측대로 헤드리스 CLI 는 그 도구를 제공하지
  않는다. 이 스펙의 인터뷰는 산문 되묻기로 성립해야 한다.
- 004 가 지원하지 않는 에이전트(Cursor 등)로의 확장.
